### 5.2 🔴 P0：双轨切换导致「错题本 / 掌握度」界面全空（数据未丢但不可见）

**触发路径（必现，无需并发）**：

```
新装 → 用错题本（库域走 JSON 轨，数据落 mistakes.json / knowledge.json）
     → 去点一次「大纲管理 / 真题考频 / 记忆卡」（那些域会 dbs.migrate() 建库）
     → 库域 _store_is_sql() 改判为 True → 错题本/掌握度改读**空库** → 界面全空
```

**实测取证**（`.workbuddy-ai/tmp/test_track_flip.py`）：

```
① 初始轨：JSON
② JSON 轨写入 3 条后：list_mistakes = 3 · list_knowledge = 1
③ 触发 migrate() 后轨：SQL
④ 此时 list_mistakes = 0 · list_knowledge = 0      ← 界面全空
⑤ 磁盘上 mistakes.json 仍存在 = True，行数 = 3      ← 数据没丢，只是读不到
⑥ 库内 mistakes 行数 = 0                            ← 没人补导
```

**根因（结构性，不是竞态）**：

| 事实 | 证据 |
|---|---|
| `core/library.py` **从不调用** `dbs.migrate()` | `grep -c migrate medkit/core/library.py` → **0** |
| `db.import_from_json()`（JSON→SQL 幂等补导）**全仓无调用方** | 只有 `db.py` 自身定义与测试引用；其 docstring 明写「避免『JSON 活数据永远进不了 DB』的丢失风险」，却从未接线 |
| db 由**别的域**按需建立 | `syllabus.py`(8 处) / `realexams.py`(5) / `cards.py`(1) 各自 `dbs.migrate()` |
| 库域的轨判定只看「db 是否存在」 | `_store_is_sql()` = `path in (...) and DB_FILE.exists()` |

即：**库域的存储轨不由库域自己决定**，而由「用户有没有点过别的功能」决定；一旦翻转且无人补导，
JSON 轨的活数据就永久读不到，此后新写入进 DB，形成真正的双轨分叉。

**副作用（性能）**：在 JSON 轨上每次**单行**写入都要把整份 JSON 原子重写一遍（含 fsync）。
实测同一操作：

| 轨 | 单条 `add_mistake` |
|---|---|
| JSON 轨（无 db） | **31.7 ms** |
| SQL 轨（有 db） | **0.3 ms** |

→ **97×**，且 JSON 轨是 O(N)（文件越大越慢）。这解释了本轮「打包产物冒烟」里
50 条批量入库耗时 7.0s（≈140ms/条）——**当时跑的就是 JSON 轨**。

**处置**：V-10（见 §7）——把库域的轨判定统一收敛到 `_sql_ready()`，在**首次**判定要走 SQL 轨时
先做一次 `db.import_from_json()` 补导（幂等 + 导入后原 JSON 改名留档 + 失败退回 JSON 轨）。

> ⚠️ **对本报告前半部分结论的修正**：§6.1 的 B1/B2/B3 治理全部作用在 **SQL 轨**。
> 对「从未建库」的安装（新装且只用了错题本/学习中心），这些优化**不生效**——他们本来就在
> JSON 轨上，每次写入是整文件重写。V-10 修好切轨时的数据可见性，**V-11 把建库与幂等补导前移到
> 启动路径**，两者合起来才让前面的优化真正落到所有用户身上。
>
> **这一节的连带教训**：本轮最初的性能基线全部在 SQL 轨上测（脚本里显式 `dbs.migrate()`），
> 于是把「JSON 轨的整文件重写」误判成了「SQL 轨 `replace_all` 的全表重插」。**评估存储性能前
> 必须先确认跑在哪条轨**——这次是靠「打包产物冒烟异常慢（140ms/条）」才反查出来的。

### 5.3 ⚠️ ADR-006 写的回滚路径**实际不可执行**（且按它执行回不到 JSON 模式）

- **事实**：ADR-006 §4「回滚方案」写「`db.downgrade_to(0)` + 恢复 `.pre-db-*.bak` 原文件名 →
  回到 JSON 模式」。但：
  ① `library._store_is_sql()` 的判据是 **`DB_FILE.exists()`** —— `downgrade_to(0)` 只 DROP 表，
     **db 文件仍在**，域模块依旧走 SQL 轨、读到的却是空表（界面又变「全空」）；
  ② `db.downgrade_to()` **全仓零调用方**，也没有任何可执行入口（`pack/` 下无回滚脚本）。
- **为什么现在必须补**：自 v0.10.3 起启动路径会自动 `migrate()` + `import_from_json()`
  （ADR-006 迁移路径 §3 / 本报告 V-11），**回滚能力是这次自动迁移的安全网**。
- **处置**：V-13 —— 新增 `pack/rollback-json-track.py`（默认 dry-run / `--yes` 执行；
  按「移走 db 文件 → 恢复 `.bak` → 回查是否真的回落 JSON 轨」的正确顺序），并**勘误 ADR-006**。
- **验收**：端到端实测「JSON 轨写 3 条 → 建库补导 → 回滚」→ 回滚后独立进程复查
  `SQL 轨 = False · 错题 = 3`（数据可见）。
