## 3. 三个必须记录的发现

### 3.1 我的第一版评测脚本有「分母陷阱」（自证伪）

首轮跑完，脚本打印 **「认可率 100.0%」**，闸门显示「通过 ✅」。**这是假的。**

原因：脚本只把「成功产出且可评审」的行放进分母（12），把契约失败的 7 题**静默排除**。
于是「7 题彻底失败」在聚合数字里消失了。真实分母应是 20。

```
口径 A（仅可评审）：12/12 = 100.0%   ← 虚高，把失败样本排除在外
口径 B（全部题目）：12/20 =  60.0%   ← 诚实口径，= 考生拿去能用的比例
```

**已修**：脚本改为同时输出两种口径，并把 B 标为结论、A 标为「仅作对照」，
且在代码注释里写明这个陷阱（`pack/stage0-attribution-eval.py` 的「口径陷阱」段）。

> 这条比数字本身重要：**任何「排除失败样本后再算成功率」的指标都会虚高。**
> 契约没过本身就是考生要承受的失败，不能被排除在分母外。

### 3.2 【生产缺陷】推理模型的 `max_tokens` 是「思考+正文」总额度

**现象**：`finish_reason=length`、`message.content=''`、HTTP 200、SDK 不报错。
上层只看到 `LLMError("模型输出为空")`，**无法区分「额度不够」与「模型真的返回空」**。

**根因**（`medkit/core/llm.py`）：`chat()` 把 `max_tokens` 当**正文**预算传给 API。
但 `deepseek-v4-flash` 是推理模型，该额度是**思考 + 正文**的总和。思考跑长了，
正文一个字都产不出来。

**对照实验**（同一题目、同一提示词，只改 `max_tokens`）：

| max_tokens | 空输出 | 详情 |
|---|---|---|
| 2000 | **3/5** | S07/S11/S15 全部 `finish=length, reasoning=2000, completion=2000` |
| 6000 | **0/5** | 同题全部 `finish=stop`，`reasoning` 最高 3806 |

`reasoning=2000, completion=2000` —— 额度被思考顶满，这是决定性证据。

**修复**（`medkit/core/llm.py`）：

1. 新增 `_truncated(resp)`：识别 `finish_reason == "length"`，**区分截断与真空**。
2. 截断时**额度翻倍重试**（2000 → 4000 → 8000，上限 32000），并记一条带
   `reasoning_tokens` 的错误留痕。
3. 新增 `except LLMError: raise` 分支——本类抛的语义化错误不得被下面的宽
   `except Exception` 重包成 `调用失败(...)` 而丢掉诊断。

**修复验证**：S07 在修复后由「失败」转为成功（`概念偷换`），日志留下
`输出被 max_tokens=2000 截断（reasoning_tokens=2000，正文为空）——推理模型需更大额度`。

### 3.3 修复本身也有 bug，被新守卫当场逮住

第一版修复用 `kwargs["max_tokens"] *= 2`。但 `kwargs` 在**每轮循环开头被重建**，
翻倍在下一轮被丢弃 → 重试仍以**原额度**发同一请求（白烧一次钱且必然再失败）。

新守卫 `tests/test_llm_truncation.py` 立刻报出：
```
assert [2000, 2000, 2000] == [2000, 4000, 8000]
```

**改为在循环外持有一个可变 `budget`**，重试才真正放大。这条记下来的理由是：
**「写了修复」不等于「修复生效」——必须以可观测的调用序列证明。**
若没有这条断言，这个空转重试会一直被当成「已经修好了」。

## 4. 守卫与反向验证

新增 `tests/test_llm_truncation.py`（10 用例），全部通过。

**注入反向验证**（把 `_truncated` 改成恒 `False` = 回到静默失败旧行为）：

```

```

注入即红 ⇒ 守卫可证伪。还原后 sha256 与注入前**逐字节一致**（`8b976d5bb0fe2302…`），
复跑 10 passed。

> 记录一次操作失误：第一次注入的锚点写成了 4 空格缩进（实际是 8 空格），
> `assert` 未命中、**注入根本没发生**，但 pytest 仍显示「10 passed」。
> 当时若就此收工，就会得出「守卫不可证伪」的**完全错误**的结论。
> **教训：注入后必须先确认文件 sha256 真的变了，再看测试结果。**

## 5. 方法学局限（结论的上界与下界）
