# MedKit 移动端迁移可行性评估

> **评估对象**：MedKit v0.19（FastAPI + 零构建原生 SPA，后端 19,088 行 / 前端 6,660 行 / 132 个端点）
> **评估时间**：2026-10-27
> **评估方式**：静态阅读 + 运行时实测（Playwright 三档手机视口，360 / 390 / 768，`is_mobile` + `has_touch`）
> **本文档不含代码改动**。结论与三档路线的取舍在第 0 节，需要你拍板的决策在第 6 节。

---

## 0. 结论先行

**"迁移"这个词在这里是误导的。** UI 层已经基本能在手机上跑（实测三档视口零横向溢出），
真正拦路的不是界面，是**这个产品的信任模型**：

> README 第 29 行写着「素材与产物全部保存在本机 `~/.medkit/`；除你自己的 AI 服务商外
> **不上传任何数据**」。而支撑这句话的是一整套硬边界：服务只绑 `127.0.0.1`、Host 头白名单
> 只放行回环地址、CSP `connect-src 'self'` 封死一切外联、**全站没有任何登录**。

所以手机端不是"适配一下"就能用，而是要在三种互斥的路线里选一条：

| | 路线 A：局域网 PWA | 路线 B：云服务 + PWA | 路线 C：微信小程序 |
|---|---|---|---|
| **手机怎么连** | 同 WiFi 连你的电脑 | 连公网服务器 | 连公网服务器 |
| **数据在哪** | 你的电脑（不变） | 云端（**承诺要改写**） | 云端（**承诺要改写**） |
| **电脑要开着吗** | **要** | 不要 | 不要 |
| **前端能否复用** | ✅ 100% | ✅ 100%（或 Capacitor 打包） | ❌ 需用 WXML 重写 |
| **后端工作量** | 小（鉴权 + 绑定 + TLS） | **大**（多租户是深改） | 大（同 B）+ 备案审核 |
| **单人估算** | **2–4 天** | **3–5 周** | **6–10 周** |
| **隐私承诺** | 不变 | 必须改写 | 必须改写 |
| **适合谁** | 你自己 / 家人都用同一台电脑 | 面向陌生用户发布 | 面向微信生态发布 |

**我的建议**：
1. 如果目的是**自己在手机上刷题**——走 A，2–4 天，投入产出比最高。
2. 如果是**要给别人用**——走 B，但先回答"LLM 的 Key 谁来付"（第 5.2 节，这是最容易翻车的地方）。
3. **不要**在小程序上复用这套代码：前端要按 WXML 重写，等于重做一个 App，而后端工作量与 B 完全相同。
4. **排除**「手机本地跑 Python」：Android 侧 PyMuPDF/jieba 尚可（Chaquopy），iOS 侧无可行路径。

还有一个更根本的判断，放在最后说：**手机不该 1:1 复刻桌面端**。
手机适合"碎片时间刷题/看错题/复习"，不适合"传 PDF 出题/逐题审核"（那是桌面端的活）。
真正该做的是**约 30 个端点的"消费面"**，而不是全部 132 个。

## 1. 现状硬事实（全部实测或代码定位）

### 1.1 手机今天连不上——不是慢，是打不开

| 事实 | 位置 | 后果 |
|---|---|---|
| 服务只绑回环 | `run_medkit.py:112` `uvicorn.run(app, host="127.0.0.1", ...)` | 手机在 WiFi 里**根本发现不了**这个服务 |
| Host 头白名单 | `main.py:207` `if hostname not in ("127.0.0.1","localhost","::1"): 403` | 即便把绑定改成 `0.0.0.0`，局域网 IP 访问也会**全部 403** |
| Origin 白名单 | `main.py:66` `_allowed_origins()` 只含三种回环写法 | 同上，写操作一律拒绝 |
| 无应用层认证 | 全仓 **0** 处入站鉴权——`Authorization`/`Bearer` 共 11 处命中，**全部是出站**调 MinerU / 博查 / LLM 服务商的请求头 | 一旦对局域网开放 = 同一 WiFi 下任何人可读写你的全部学习数据 |

这三道闸是**有意设计**的（注释写明防 DNS rebinding 与 CSRF「烧钱」），不是疏漏。
所以路线 A 的第一步不是"改绑定"，而是**在打开一个受控口子的同时补上身份**。

### 1.2 数据层是"单机单用户"写死的

```python
# medkit/core/config.py:27
CONFIG_DIR = Path(os.path.expanduser("~")) / ".medkit"
```

而 `tests/browser/server_launcher.py` 的注释点出了关键约束：

> `medkit` 的核心模块（config / db / library / review / explain / tutor / state）都在
> **import 时**把 `cfg.CONFIG_DIR` 派生的常量绑定到模块级变量（如 `LIBRARY_DIR`、`DB_PATH`、
> `OCR_JOB_DIR`、`PRESETS_DIR`）……所以真正的隔离必须在「import medkit.main 之前」重设。

**这句话就是路线 B 的最大成本来源**：多租户要求"同一个进程里，A 用户和 B 用户看到不同的
数据根"，而现在这些路径是**进程级常量**。要么一进程一用户（部署复杂度爆炸），
要么把这些常量改成请求级上下文（触及 core 下所有模块）。

配套的还有其他单机假设：

| 单机假设 | 位置 | 云化影响 |
|---|---|---|
| 全局可变状态按 `pid` / `job_id` 键，无用户维度 | `medkit/state.py`（`RUNNING` / `RUN_THREADS` / `OCR_JOBS`） | 两个用户的 `pid` 理论上会撞（都用 `p_xxx`），必须加用户前缀 |
| OCR 并发信号量全局 2 | `state.py:23` `OCR_SEM = Semaphore(2)` | 多用户时一个人就能占满，需改按用户配额 |
| 数据库表无 `user_id` | `db.py`：`syllabus_items` / `realexam_freq` / `cards` / `kp_alias` / `error_events` / `meta` | 要么加列（全表迁移），要么一用户一库文件（推荐） |
| 长任务是内存线程 + 轮询 | `routers/pipeline.py`、`routers/ocr.py` | 进程重启即丢（lifespan 主动 cancel），多副本部署无法共享状态——需要真正的任务队列 |
| 端点回传绝对路径 | `routers/data.py:152-155` `"dir": str(root)` | 云上属于目录结构泄漏 |

### 1.3 前端：移动端适配程度比预期高得多

我起真实服务、用移动 UA + 触摸仿真实测了三档视口、五个主页面：

| 视口 | 横向溢出 | 可点元素 | 命中区 <24px |
|---|---|---|---|
| 360×740（iPhone SE / 小屏安卓） | **0** | 17–61 / 页 | 1（版本号，恰好 24px，达 AA 下限） |
| 390×844（iPhone 14） | **0** | 同上 | 1 |
| 768×1024（iPad 竖屏） | **0** | 同上 | 1 |

输入控件计算字号 **15px**；拖拽（配比条）用的是 `pointerdown` + `setPointerCapture` 且
`.segbar` 已设 `touch-action:none`；`@media (hover:none)` 已放大 `.seghandle` 与 `.mini-btn`；
≤860px 侧栏已是底部导航条。

**结论：布局与交互基本就绪，剩下的是 5 个具体缺陷 + 2 个能力缺口（见第 4 节）。**

### 1.4 规模盘点（用于估算工作量）

| 维度 | 数值 |
|---|---|
| 后端 | 73 个 py 文件 / 19,088 行 |
| 前端 | 15 个 js / 6,660 行（+ HTML/CSS） |
| API 端点 | **132** 个（GET 51 / POST 63 / 其他 18） |
| 流式端点 | 2 个（`/api/vault/ask`、`/api/vault/handbook`，POST + fetch 流式，手机端兼容） |
| 数据库表 | 7 张，**全部无用户维度** |
| 测试 | 1,190 项（单元 1,134 / 浏览器层 56） |
| Windows 专有代码 | 3 处（隐藏文件属性、`os.startfile` 打开目录、其平台判断）——**云化几乎无成本** |

## 2. 路线 A：局域网 PWA（电脑当服务器）

**适用**：自己用 / 家人共用同一台电脑。**估时 2–4 天。**

### 要做的事

| # | 事项 | 位置 | 说明 |
|---|---|---|---|
| A1 | 绑定与放行 | `run_medkit.py:112`、`main.py:207`、`main.py:66` | 改为可配置绑定 + **允许"本机 IP 段"**（而非任意 Host），Origin 同步放行 |
| A2 | 一次性配对码 | 新增 | 启动时在**桌面端**显示 6 位码，手机首次访问输入后换 HttpOnly Cookie。**没有这步，等于把全部数据挂在 WiFi 上** |
| A3 | HTTPS | `run_medkit.py` | PWA 的 Service Worker 要求安全上下文；`127.0.0.1` 例外，**局域网 IP 不例外**。需自签证书（手机首次会警告）或 mkcert |
| A4 | PWA 化 | 新增 `manifest.webmanifest` + `sw.js` | 可"添加到主屏"、离线打开壳、缓存静态资源 |
| A5 | 令牌限速 | 新增 | 配对码必须限次数（6 位码在局域网内可被暴力猜） |

### 风险

- **电脑必须开着且同一 WiFi**——学生在教室/通勤路上用不了，这是路线 A 的硬上限。
- 自签证书在 iOS 上的信任流程较绕（需手动信任描述文件），会让非技术用户卡住。
- 家里的 WiFi 若开了"AP 隔离"，手机直接连不上。

**判断**：如果只是"想在床上/沙发上刷题"，A 值得做，且两天能出可用版本。

## 3. 路线 B：云服务 + PWA

**适用**：面向陌生用户发布。**估时 3–5 周（单人）。**

### 3.1 必做清单（按依赖顺序）

| # | 事项 | 说明 | 量级 |
|---|---|---|---|
| B1 | **数据根请求级化** | 把 `core/*` 里 import 期绑定的 `LIBRARY_DIR` / `DB_PATH` / `OCR_JOB_DIR` / `PRESETS_DIR` 改成"按当前用户解析" | **最大块，1–1.5 周** |
| B2 | 账号体系 | 注册 / 登录 / 会话 / 找回；密码哈希；可选微信扫码登录 | 3–5 天 |
| B3 | 存储隔离 | 一用户一 SQLite 文件（最省事）或加 `user_id` 列（要全表迁移）；vault 目录按用户分区 | 3–5 天 |
| B4 | 全局状态加用户前缀 | `RUNNING` / `RUN_THREADS` / `CANCELLING` / `OCR_JOBS`；`OCR_SEM` 改按用户配额 | 2–3 天 |
| B5 | 长任务持久化 | 现在线程 + 内存字典，重启即丢。云端必须落库 + 断线重连（手机锁屏就断流） | 3–5 天 |
| B6 | 路径与下载改造 | `data.py` 回传的绝对路径改逻辑路径；备份/导出走签名 URL 或直接流式 | 1–2 天 |
| B7 | 部署 | 反代 + TLS + 进程守护；**注意** `OCR_SEM=2` 对 MinerU 是限频保护，多用户要重新算配额 | 2–3 天 |

### 3.2 容易被低估的三件事

**① 「按 import 期常量」是全仓性的**
不是改一个文件。`core/library.py`、`core/db.py`、`core/vault.py`、`core/config.py`、`state.py`
都以模块级常量持有路径——而 `tests/browser/server_launcher.py` 正是因为这一点才用**独立子进程**
做测试隔离。云化等于把这个"隔离靠进程"的假设改成"隔离靠上下文"，属于架构层手术。
**好消息**：你有 1,190 项测试兜底，这类重构的安全性比一般项目高得多。

**② 手机锁屏 = 长任务断流**
项目管线（出题/审核）是分钟级；OCR 轮询、SSE 问答都靠前端保持连接。
iOS 在切后台后很快挂起定时器与 fetch。现在的实现**没有** `visibilitychange` 恢复逻辑
（全仓 0 处），所以：锁屏 → 回来 → 进度条停在旧状态。云版必须做「任务态在服务端、前端只做订阅」。

**③ 成本模型会变**
现在是「用户自己的 API Key + 用户自己的电脑」，边际成本为 0。
变成云服务后，Key 放在服务端 = **你在替所有人付 LLM 费用**（出题、审核、问答、手册生成全是长文本）。
见第 5.2 节。

## 4. 路线 C：微信小程序 —— 不建议复用本代码库

| 事实 | 影响 |
|---|---|
| 小程序用 WXML/WXSS，不是 HTML/CSS | 6,660 行 JS + 全部模板**需要重写**为 WXML，`innerHTML` 范式完全不适用（小程序无 DOM） |
| 请求域名必须在后台备案 + HTTPS + 不可用 IP | 需要域名、ICP 备案、SSL |
| 包体积 2MB 主包限制 | 现在前端全量 **473KB**（HTML+CSS+JS 未压缩），换算成 WXML 后仍需留意 |
| 审核 | 涉及"题库/AI 生成"内容，审核口径需预判 |

**工作量 ≈ 路线 B 的后端 + 一个全新前端（6–10 周）。**
唯一优势是分发（微信里点开就用、可分享）。如果目标用户是"同学之间传播"，这是最强的渠道；
但它不是"迁移"，是"再造一个客户端"。

## 5. 关键风险

### 5.1 隐私承诺冲突（必须先解决，不是技术问题）

README 第 29 行是产品对用户的核心承诺。走 B/C 就必须改写它，而且要给出新的等价承诺
（例如「数据加密存储、仅你本人可读、可随时一键导出并删除」）。**这件事应该在写第一行代码前定。**

### 5.2 LLM 费用归谁（最容易翻车）

现状：用户自己填 API Key，Key 加密存在本机，调用发生在本地后端。

| 方案 | 用户体验 | 你的成本 | 风险 |
|---|---|---|---|
| 服务端统一 Key | 最好（开箱即用） | **线性增长，且不可控** | 被刷接口 → 账单失控 |
| 用户自带 Key | 差（要先注册个 AI 服务商） | 0 | 大量用户流失 |
| 混合（免费额度 + 自带 Key） | 折中 | 可控 | 需要计量、限流、反滥用 |

代码里已有 `core/usage.py`（token 记账 + 硬上限 `BudgetExceeded`），**这是现成的地基**，
但它现在是"单机自用"的记账，云端要扩成"按用户配额"。

### 5.3 长任务与手机后台

见 3.2 ②。另外 132 个端点里有 63 个 POST，其中有若干是"分钟级同步阻塞"的
（上传解析、OCR、出题）。这类端点在移动网络下超时率会显著高于本机。

### 5.4 你现在的安全护栏会被削掉

`Host` 白名单、`Origin` 白名单、`Sec-Fetch-Site` 拦截、CSP `connect-src 'self'`
——这四层是为"只在本机"设计的。云化后它们要么失效，要么必须换成等价的真实防护
（CSRF token、鉴权中间件、CORS 精确白名单）。**不要在打开口子时顺手把它们删了。**

## 6. 移动端的"消费面"切分（推荐的产品形态）

手机不需要 132 个端点。按使用场景切：

| 场景 | 手机 | 桌面 |
|---|---|---|
| 刷题 / 背题 / 答题卡 | ✅ 主战场（碎片时间） | 可用 |
| 错题本 / 本地错题 / 今日复习 | ✅ 主战场 | 可用 |
| 薄弱点诊断 / 学习看板 | ✅ | ✅ |
| 错题助手问答（SSE 流式） | ✅（需处理锁屏断流） | ✅ |
| 导入 PDF / DOCX 建题库 | ⚠️ 能传但不适合（大文件 + 解析几分钟） | ✅ 主战场 |
| 出题 / 押题卷 / 逐题审核 | ❌ 屏太小 | ✅ 主战场 |
| 题库管理 / 提示词 / 服务商配置 | ❌ | ✅ |
| 数据备份 / 清空 | ❌ | ✅ |

**估算消费面约 30 个端点**（`bank` 的作答与判分、`library` 的错题与诊断、`vault` 的列表/统计/问答、
`review` 的排期），不到总数的四分之一。这意味着：
- 云化时可以先只搬这 30 个，桌面端保持本地 → **混合形态**，成本立减。
- 小程序若真要做，也只需实现这 30 个对应的页面。

## 7. 移动端现存缺陷清单（无论走哪条路线都要修，约半天）

这些是**实测出来的、与架构无关**的小问题。按性价比排序：

| # | 问题 | 位置 | 影响 | 改法 |
|---|---|---|---|---|
| M1 | `viewport-fit=cover` 缺失 | `index.html:5` | 上一轮我为底部导航加的 `env(safe-area-inset-bottom)` **恒为 0** —— iPhone 上导航条会被 Home 指示条压住 | viewport 加 `viewport-fit=cover` |
| M2 | 输入控件字号 15px | `base.css:79`（`--fs-3`） | iOS Safari 聚焦时自动放大页面，且**不会缩回**——填表单时体验很差 | 输入类单独设 `font-size:max(16px, var(--fs-3))`（别动正文） |
| M3 | toast 被底部导航遮挡 | `base.css:276` `bottom:24px` | 窄屏下 toast 落在 76px 高的导航条区域内，文字被压 | `bottom:calc(76px + env(safe-area-inset-bottom,0px) + 12px)`（仅窄屏） |
| M4 | `body{min-height:100vh}` | `base.css:8` | 移动端工具栏收放时高度跳动（侧栏已改 `dvh`，body 漏了） | 改 `100dvh`（保留 `100vh` 兜底） |
| M5 | 无 `manifest` / Service Worker | 新增 | 不能"添加到主屏"，无离线壳 | 仅路线 A/B 需要 |
| M6 | 3 处 `setInterval` 无 `visibilitychange` 恢复 | `bank-drill.js:72,115`、`review-desk-project.js:437` | 锁屏回来进度停在旧状态 | 监听 `visibilitychange` 重新拉状态 |
| M7 | 无 `theme-color` | `index.html` | 手机浏览器地址栏颜色与深色主题不搭 | 加 `<meta name="theme-color">` |

**注意 M2 的陷阱**：`--fs-3:15px` 同时被正文、按钮、输入共用。直接改令牌会放大全站正文，
应当只对 `input/select/textarea` 单独处理。

## 8. 需要你拍板的决策

1. **目标是谁**：只自己用（→ A）／给同学朋友用（→ B）／公开产品（→ B 或 C）？
2. **数据能不能上云**：README 的「不上传任何数据」是否可以改写？如果不能，只有 A 一条路。
3. **LLM 谁付钱**：服务端统一 Key（体验好、成本不可控）／用户自带（成本 0、流失高）／混合？
4. **是否接受"电脑必须开着"**（路线 A 的硬前提）？
5. **要不要只做"消费面"**（刷题/错题/复习）而不复刻出题与审核？

## 9. 如果现在就要动，我建议的顺序

```
第 1 步（半天，零风险）：修 M1–M4、M7 —— 纯 CSS/meta，桌面端完全不受影响
第 2 步（1 天）：加 manifest + SW 骨架，手机"添加到主屏"可用（仍限本机）
第 3 步（2–3 天）：路线 A —— 绑定/Origin 可配置 + 配对码 + 自签 HTTPS
第 4 步（决策后）：若要走 B，先做 B1（数据根请求级化）—— 这是唯一不可绕过的深水区
```
