# 前端「AI 味」调研与改法（2026-10-28）

> **结论先行**：这个仓的 AI 味不是某一句话写坏了，而是**三层叠加**——
> ① 把「实现记录」当「产品说明」写（README 重灾区）；② 用「长段落解释」代替「信息层级」（UI 通篇 hint）；
> ③ 产品叙事默认「AI 生成 / 一键 / 全新」，把内部术语（闭环/沉淀/门禁/溯源）直接端给用户。
> 再加一个结构性原因：**有 1357 项代码守卫，却没有一条文案守卫**——AI 味不会让任何测试变红，所以它只会越积越厚。
> 搜索侧另有一个硬缺口：**应用内「我的题库」没有搜索框**（`routers/bank.py:130` 的 `list_banks()` 无任何查询参数），
> 搜索只存在于「导出的题库 HTML」和「错题本」里。这直接对应「多人搜题」的痛点。

---

## 0. 先说清楚：我不认为这是「作者不会写」

以下判断都基于**可复核的文本特征**，不推测作者意图。这些特征高度符合「LLM 辅助起草 + 工程师直接贴进产品」的产物，
但更准确的说法是：**没人专门为"读者"重写过一遍**。代码有 review，文案没有。

## 1. 什么叫「AI 味」：6 个可证伪的标记

不用"感觉"来判断，用能指到行号的特征：

| # | 标记 | 长什么样 | 本仓实例（file:line） |
|---|---|---|---|

## 2. 根因：为什么这个仓会积累 AI 味（5 条，按影响排序）

1. **写作主体错位：README 是"实现日志"，不是"产品说明"。**
   `README.md:106` 起的「已实现功能」把每一版的内部决策（FSRS 参数、BKT 收缩、迁移 v11、1357 项 pytest）
   原样写给用户。这些内容对**维护者**有价值，对**第一次打开软件的人**是噪音。
   → 根因不是"AI 写的"，而是"**没有第二个读者视角**"。

2. **内部术语外化**：闭环 / 沉淀 / 溯源 / 门禁 / 契约 / 读模型 / 可弃索引。
   在代码注释里这些词精确；在 UI 和 README 里，用户不知道"闭环"指什么。
   `index.html:94`「学习闭环总览」、`README.md:117` 整段都是这类词。

3. **产品叙事绑定 AI**：这个软件的核心卖点确实是"用 AI 从教材出新题"，于是文案默认
   "AI 生成 / 一键 / 全新"。但**刷题与错题复盘根本不需要 AI**（`index.html:399` 自己都写了
   「日常刷题与错题复盘不需要它」）——叙事却没跟上这个事实。

4. **排版偷懒：用"长 hint 段落"代替"层级"。**
   `index.html` 几乎每张卡片下面都挂一段 2~4 行的 `.hint`，加粗关键词、塞括号。
   这是**最快**的写法（写段落比设计标题/标签/提示三层快），也是 AI 味最直观的来源。

5. **没有文案守卫。** 本仓的工程纪律极强（断言审计、skip 审计、悬空引用守卫、前端分域耦合守卫……），
   唯独**用户可见文案没有任何自动化约束**。既然不会变红，它就会持续劣化。

## 4. 排版改法：从「段落解释」到「层级 + 渐进披露」

`index.html` 的结构问题不是丑，而是**每张卡片的信息密度都一样**——标题、说明、按钮全是同一视觉权重，
于是只能靠"加粗 + 括号"来强调，越加越像 AI 写的。

### 4.1 三条硬规则

1. **一屏一任务，一卡一句话。**
   卡片头只放「标题 + 一句价值」，例如「我的题库 · 导入后即可刷」。删除卡片内的第二、三段解释。
2. **理由下沉。** 任何"为什么这样设计"都进 `title` 属性、`<details>` 或帮助页；卡片正文只留"做什么、怎么点"。
   现在的 `:377-378`、`:330-331`、`:299-301` 都是典型可下沉段落。
3. **提示分级，而不是加粗。**
   - 必须知道 → 卡片正文（≤1 行）
   - 可能踩坑 → 输入框旁 `?` tooltip
   - 实现细节 → 帮助文档
   现在所有东西都挤在 `.hint` 里用 `<b>` 区分，读者无法建立优先级。

### 4.2 版式微调（低成本、高收益）

- **空状态**统一成「一句现状 + 一个主按钮」，不要"大图标 + 引导文案 + 再解释一遍"。
- **危险操作**（清空数据）保留红色边框，但把"不可逆"放按钮旁一行，而不是整段解释。
- **`README` 首屏**：标题下第一屏只放「一句话定位 + 3 个能力 + 1 张截图 + 安装一行」。
- **术语表**：把"闭环/沉淀/溯源/门禁"统一收进 docs/glossary.md（建议新建），UI 里改用大白话（"复习进度""错题归集""能查到出处""自动检查"）。

## 5. 「多人搜索」：现状、缺口、三步方案

### 5.1 现状（先承认已有的）

| 位置 | 有没有搜索 | 证据 |
|---|---|---|
| 导出的题库 HTML | ✅ 有（题干/考点/章节） | `medkit/render/qbank_html.py:499` `#qsearch`，`:569` 过滤时跨页显示全部匹配 |
| 错题本 / 本地错题 | ✅ 有关键词检索 | `medkit/web/js/learn-vault.js:117` 空状态即"换个关键词" |
| **应用内「我的题库」列表** | ❌ **没有** | `medkit/web/js/bank.js` 全文无 `search`；`routers/bank.py:131 list_banks()` 无参数 |
| **应用内「开始刷题」选题** | ❌ **没有** | `routers/bank.py:294 drill()` 只有 `mode`/`limit` |

### 5.2 缺口说明（为什么这件事对"多人"重要）

"多人"在本产品里的真实形态是：**一个学习小组共用同一份题库文件**（本地优先，靠导入/导出共享）。
一旦题库到几千题，当前只能：
- 导出成 HTML 再去搜 → **丢了作答/错题/掌握度的联动**；
- 或者一页页翻「题目管理」→ 不可用。

所以"便捷多人搜索"的本质是：**在应用内，用一次输入就定位到某道题，并且能直接进入练习/查看解析。**

### 5.3 三步方案

**P0（半天~1 天，纯前端）— 题库列表加搜索**
- 在 `index.html` 的「我的题库」卡（`:132-152`）加一个 `<input type="search">`，按题库名/科目过滤。
- 在「题目管理」表格（`bank.js:231` 渲染）加搜索框，**前端过滤已加载的 items**（题干/选项/考点）。
- 复用导出页的归一化逻辑（`core/bank_iq` 的归一函数），避免"搜'慢阻肺'搜不到'慢性阻塞性肺疾病'"。
- 空状态照抄 `learn-vault.js:117` 的写法，保持全站一致。

**P1（1~2 天，前后端）— 全局搜索进 `Ctrl+K` 命令面板**
- 后端加 `GET /api/bank/search?q=&limit=`，返回 `[{bank_id, item_id, stem, topic, matched_in}]`。
- 前端 `palette.js` 增加一个"题目"结果组，回车**直接跳到该题的沉浸式作答**（复用 `bank-drill.js`）。
- 这是"多人搜题"的核心体验：**一个输入框，搜题库 + 搜错题 + 搜考点**。

**P2（按需）— 大题库上 FTS5**
- `docs/adr/ADR-002-fts5-jieba-retrieval.md` 已经决策过 FTS5 + jieba，但题库域目前没接。
- 题库 > 2k 题再上；小题库用 `LIKE` / 前端过滤即可，别提前优化。
- 索引字段：题干、选项、解析、考点；**分词用 jieba 医疗词典**，否则"慢阻肺"会被切碎。

> 共享题库的附带建议：导出题库时保留 `id` 与 `source_ref`，让组员导入后**错题能对回原题**
> （本仓已经踩过 `sync_from_paper` 覆盖 `source_ref` 的坑，见 `core/bank.py`）。

## 8. 防回归：把「AI 味」变成会变红的测试

这是本仓最该补的一环——**没有守卫的规范等于没有规范**。建议加 tests/test_copy_tone.py（建议新建，静态扫描，不联网）：

1. **禁用词表**（用户可见字符串 + README 首屏）：
   `一键` `全新` `赋能` `打造` `助力` `一站式` `闭环`（UI 层）`极致` `完美`
   → 命中即 fail，附"文件:行 + 建议替换"。
2. **长度上限**：`index.html` 里单个 `.hint` 文本 ≤ 60 字；README 单条 bullet ≤ 80 字（技术细节除外，白名单登记）。
3. **括号深度**：单句 `（）` 嵌套 ≤ 1 层。
4. **emoji 白名单**：UI 正文禁止装饰性 emoji（`✓ ✗` 等状态符号放行）。
5. **元守卫**：用内存样本自证"注入一句『一键赋能』必须红"——这是本仓其它守卫的既有做法。

> 这样「AI 味」第一次有了反馈回路：写文案时会被拦，而不是等用户说"太像 AI 了"。

## 落地记录（第三轮）：P1 全局搜题已接进 Ctrl+K

报告里规划的「第二步：一个入口搜题库 + 错题 + 考点」先落了**题库这一段**（错题与考点仍在队列）。

**后端** `GET /api/bank/search`（`core/bank.search_items`）：

- 口径：空白切词，**每个词都要出现**（AND，不是并集）。`data LIKE` 只拿**最长的那个词**做预筛
  （选择性最好，也省掉拼一长串 LIKE）；其余词在 Python 里 AND——**预筛只是优化，判定唯一来源
  是 `_search_rank`**，所以预筛写窄了也不会漏结果，只会变慢。
- 排序：题干全中 > 题干部分命中 > 只命中其它字段；同档按命中词数、再按题干长度
  （关键词占题干比例越高，越像"就是问这个"）。
- 边界写清楚：**不做同义词**。「慢阻肺」搜不到只写「慢性阻塞性肺疾病」的题——那需要一份
  医学别名词典，`bank_iq` 的归一只动格式不动语义，替代不了。词表方案见 `docs/adr/ADR-002-fts5-jieba-retrieval.md`。
- 实测（2000 题，本机）：单次 60~96ms。前端防抖 140ms ⇒ 体感约 0.2s；万题级必须走 FTS5。

**前端** `palette.js`：列表从「一维命令数组」变成 `{kind:"cmd"|"item"}` 混排——命令在前、
题目在后，中间一条分段标题。三点约束：140ms 防抖 + **请求序号丢弃过期响应**（连打四个字会发
四次请求，只有最后一次能落地）；搜索失败只少一段结果、**不让面板变哑**；空输入不发请求。
点中题目弹**只读预览**（题干 / 选项 / 答案 / 解析 / 出处，复用 `.trialq` 试做卡样式）——
搜题多半是"确认一下这题怎么写的"，跳页会丢掉搜索现场。

**顺带修的一个真缺陷**：`bank_items.qtype` 冗余查询列**恒为 NULL**（data 里字段名是 `type`，
而 `put_row` 按列名取值）。与 `topic`（字段名是 `subtopic`）同族——「列名与 data 对不上」
第二次复发。目前没有查询依赖它，但已纠正并加守卫钉住。

**守卫**：`test_bank` 新增 9 条（命中字段 / 多词 AND / 选项可搜 / 题干优先 / 空输入 / limit 与
total 分离 / 单库限定 / LIKE 转义 / qtype 列真被写入），全部实测「注入缺陷即红」；
浏览器层加 1 条端到端（搜题 → 分段标题 → 点开预览 → 只读无「取消」）。

**顺带发现**：README 的测试计数此前**偏 2**（登记 1363、实际 1365），已按 `pytest --collect-only`
真实值校正。这类数字一旦没有守卫就会慢慢腐烂——本轮恰好证明了守卫有用（改完 CSS 忘了同步
`dist/`，`test_installer_payload_contains_sources` 当场变红）。

### 2. 提示词：正面 3 条不够，得有禁用 5 条

`medkit/prompts/mistake_agent.md` 的语气段改成「必须 4 条 / 禁止 5 条」。道理和代码里的守卫一样：
**只写正面描述的提示词，等于没有约束**——LLM 会回弹到默认人格（「好的，希望这对你有帮助」）。
「没有依据时硬凑一段通识」被归到第 2 条硬规矩里，因为它不是文风问题，是会毁掉引用纪律的行为。

### 3. README 分层：首屏给用户，账本给维护者

「已实现功能」从 40+ 条等权 bullet（单条最长 800 字）压到 **11 条用户视角条目**；

  下次改文案照着查，不必再读一遍这份报告。

### 4. 搜索：三段聚合，而不是前端连发三个请求

`GET /api/palette/search` 一个请求取回「题目 / 错题 / 考点」。在服务端聚合的两个理由：

1. **截断口径要在一处**：`limit` 是**每组**上限，不是总数——否则最长的那段会把面板撑满，
   另外两段等于不存在（用例 `test_limit_is_per_group_not_total` 钉住）。
2. **一段坏不拖垮其余**：每组独立 `try/except`，失败的域缺席并把原因带进 `errors`。
   前端 `catch` 只兜得住网络层，兜不住"某个域的索引坏了"。

两个交互决定：**错题预览要带出「我的理解 / 我的疑问」**（错题的价值不在题干，在用户自己写的话）；
**考点点击不关面板**，而是用考点名再搜一轮（意图是"看这个考点的题"，收掉面板反而要重新唤起）。

### 5. 故意没做的一件事：FTS5

报告 5.3 的 P2 写的是「**题库 > 2k 题再上**；小题库用 LIKE / 前端过滤即可，**别提前优化**」。
本轮实测（2000 题、本机）：`/api/bank/search` 单次 60~96ms，前端 140ms 防抖后体感约 0.2s。
按这个判据现在不该上 FTS5——它要新增一张索引表 + 迁移 v13 + 在每条写路径上维护，
而收益要到万题级才看得见。**触发条件写在这里**：题库过 2k 题、或单次检索稳定超过 200ms，
就按 `docs/adr/ADR-002-fts5-jieba-retrieval.md` 接 FTS5（jieba 已在 `db.fts_tokens` 里，
不用新增依赖）。
