## A. 数据完整性（最该先修）

### W1 ✅ `slices.json` / `stage.json` 非原子写 —— 崩溃即项目报废

**具体表现**：同一个文件里，`meta.json` 走了原子写，`slices.json` 却是裸 `write_text`：

```python
# medkit/core/projects.py:64   ← 原子
write_json_atomic(base / "meta.json", meta)
# medkit/core/projects.py:120  ← 非原子（复核确认）
(proj_path / "slices.json").write_text(
    json.dumps(all_slices, ensure_ascii=False, indent=1), encoding="utf-8")
# medkit/core/projects.py:150  ← 非原子（stage.json 同样）
(proj_path / "stage.json").write_text(...)
```

`core/fsutil.py:38` 已有现成的 `write_json_atomic`（唯一 tmp 名 + `tmp.replace(path)` + 6 次 Windows 共享冲突重试，`:41-52`）。**两条路径不一致**本身就是信号：`upload_asset` 路径用的是原子写，建项目路径漏了。

**影响**：建项目瞬间进程被杀 / 断电 / `taskkill` → 留下**截断的 `slices.json`**。之后：
- `orchestrator._run_project_impl:1163` `json.loads((base/"slices.json").read_text())` 直接抛异常 ⇒ **项目永久无法生成**；
- `routers/projects.py:_image_slices` 静默返回 `[]` ⇒ 图片切片消失。

**触发条件**：写入 `slices.json` 的那几毫秒内进程消失（建项目时用户切走 / 关掉程序 / 系统休眠）。
**爆炸半径**：单个项目不可恢复（需手工修 JSON 或重建）。

**改进方案**：
```python
# projects.py:120 与 :150 —— 改为
write_json_atomic(proj_path / "slices.json", all_slices)
write_json_atomic(proj_path / "stage.json", {"stage": "quota", "updated": ...})
```
顺带把生成过程中其余产物写盘（`orchestrator.py:1279` `questions_raw.json`、`:1414` `questions_final.json`、`:1454` qbank）一并统一到 `write_json_atomic`。**成本极低（纯粹替换函数名），收益最高。**

**验证方式**：新增守卫用例 —— 用 monkeypatch 让 `json.dumps` 抛异常，断言**目标文件仍是旧的完整内容**（不是半截）。**注入反向验证**：把 `write_json_atomic` 换回 `write_text` → 该用例必须红（这才是「检查会拦」的证明）。

### W3 ✅ `questions_final.json` 不在内部黑名单 —— 截断产物可被下载

**具体表现**：内部产物黑名单（`routers/projects.py:202`）：

```python
_INTERNAL_ARTIFACT_NAMES = frozenset({
    "meta.json", "slices.json", "stage.json", "progress.json",
    "questions_raw.json", "questions_gate1.json", "checkpoint.json", "paper_ids.json",
})
```

**`questions_final.json` 不在其中**——而 `questions_raw.json` / `questions_gate1.json` 都在。这是明显的一致性缺口（同类文件，一半进黑名单）。

**影响**：`questions_final.json` 用裸 `write_text` 写（`orchestrator.py:1414`），崩溃→截断。因为不在黑名单，它可以被**下载/预览**（`projects.py:289` 的黑名单检查放行），用户拿到一个语法不完整的 JSON；`export/apkg` 路径 `json.loads` 它 → 500。
**触发条件**：崩溃发生在写 `questions_final.json` 时（概率低，但产物是用户主要交付物）。
**爆炸半径**：产物可信度受损（「下载的文件打不开」）。

**改进方案**：① 把它加入 `_INTERNAL_ARTIFACT_NAMES`（但要注意：它可能确实需要被导出 —— 先确认它是否出现在产物列表；若需要导出，则**只修原子写，不进黑名单**）；② **无论如何都改为 `write_json_atomic`**。
> ⚠️ 落地前必须**先查清它是否有意暴露**——这正是「不越权推翻既有产品决策」的边界：如果它是给用户下载的，就不能拉黑，只能修原子性。

**验证方式**：若决定拉黑 → 断言 `project_file(name="questions_final.json")` 返回 404/403；若决定保留 → 断言它写入是原子的（同 W1 的崩溃用例）。

### W11 `delete_asset` 无 dry-run / 软删除

**具体表现**：`routers/projects.py:457` 直接 `f.unlink()` + 改 `slices.json`，无备份、无 dry-run（对比 `data.py:238` 清空数据要求输入短语 + 自动全量备份 `:245`；`library.py:199` 批删先导出备份）。
**影响**：误删一张图不可恢复。**触发条件**：用户点错 + 前端 confirmModal 被绕过/误确认。
**改进方案**：对齐项目既有不变量——删除前把文件 `rename` 到 `assets/.trash/`（而非 `unlink`），或加 `dry_run: bool` 参数。前端 confirmModal 已存在，后端补一层即可。
**验证方式**：断言删除后文件仍在 `.trash/` 且可 `restore`；**注入即红**：把 `rename` 换回 `unlink` → 用例必须红。

## B. 失败模式（最隐蔽）

### W2 ✅ 门禁① 五子步骤失败 → 静默当「无问题」放行

**具体表现**：`orchestrator.py:819-865`，五个子校验各自 `if xxx_err:` 后**把问题集清空并继续**（复核确认，五处齐全）：

```python
_opt_issues, opt_err = _run_substep(... "选项校验" ...)
if opt_err:
    _append_manual_section(base, "门禁① 选项校验",
                           [f"...失败：{opt_err}", "已按无问题继续，建议人工复核。"])
    _opt_issues = []          # ← 门禁结果被替换为「无问题」
# bloom / trace / dup / numeric 四处同构（:829, :840, :851, :862）
```

**影响**：校验子步骤超时/异常时，**未校验的题库被当作「已通过门禁」**进入产物。这是典型的 **plausible-but-wrong**：产物看起来正常，实则门禁从未生效。留痕仅落在「人工复核清单.md」+ `_qc_notice`（且那是 QC 提示，**gate1 失败不显示在产物页**）。
**触发条件**：任一 `_run_substep` 抛错（超时、依赖缺失、数据畸形）。概率中——恰恰是「输入越脏越容易触发」。
**爆炸半径**：**用户收到未经质检的题目却以为已质检** —— 对「医学考试题库」这是最高等级的正确性风险。

**改进方案**（分两档，建议同时做）：
1. **可区分状态**（核心）：把 `_opt_issues = []` 改成 `_opt_issues = None`（或加 `"failed": True` 标志），语义从「无问题」变为「**未校验**」。前端产物页显式区分三态：✅通过 / ⚠️有问题 / ⛔**未校验**。这直接命中项目自己的总原则——**「检查通过」与「检查没跑」必须能区分**（MEMORY 一）。
2. **可配置策略**：新增开关 `gate1.fail_policy ∈ {continue, abort}`。默认 `continue`（保持离线可用），但**产物页必须显示⛔**；严格模式可 `abort`。

**验证方式**：
- 断言「子步骤抛错 → 门禁结果字段 == `None`（不是 `[]`）」（**这是「可区分」的直接证明**）；
- **注入反向验证**：把 `= None` 改回 `= []` → 用例必须红；
- 断言「⛔未校验」在产物 HTML 中真实渲染（不是只在内部 JSON）。

## C. 安全

### W4 ✅ `base_url` 无校验 → SSRF

**具体表现**：`routers/config.py:177` `TestBody.base_url` / `:196` `ModelsBody.base_url` 由用户直接提供，**原样传给 SDK**（复核确认）：

```python
# routers/config.py:177
client = LLMClient(body.base_url, key, body.model, timeout=8, max_retries=1)
```
全仓 `grep is_private|urlsplit|169.254` 在 `llm.py`/`config.py` **零命中** ⇒ 无任何 scheme/host 校验。用户可填 `http://169.254.169.254/latest/meta-data/` 或 `http://127.0.0.1:<内网端口>`，服务端会带 `Authorization: Bearer <key>` 发起 POST 并回显响应片段。

**影响**：云主机场景可探测元数据服务 / 内网端口扫描；`openai` SDK 不接受 `file://`（httpx 抛错），故无本地文件读取。
**触发条件**：用户在「自定义端点」处填入恶意/内网地址。
**爆炸半径**：**本机单用户场景有限**（密钥是用户自己的），但若 MedKit 跑在云 VM 上则真实可被自己或恶意配置利用。

**改进方案**：在 `TestBody`/`ModelsBody` 加 pydantic validator：
```python
@field_validator("base_url")
@classmethod
def _check_url(cls, v: str) -> str:
    u = urlsplit(v)
    if u.scheme not in ("http", "https"): raise ValueError("仅支持 http/https")
    host = (u.hostname or "").lower()
    if host in ("localhost",) or ipaddress.ip_address(host).is_private if _is_ip(host) else False:
        raise ValueError("不允许指向本机/内网地址")
    return v
```
> ⚠️ **必须留逃生口**：本地部署常需连 `http://127.0.0.1:11434`（Ollama）这类本机模型 —— **默认拒绝会打断真实用法**。因此建议**默认警告不拒绝**，或加白名单配置 `allow_private_endpoints: true`。这是典型的「收紧安全会误伤合法用法」（MEMORY 一「排除式判据常假红」）。

**验证方式**：断言 `base_url="http://169.254.169.254/"` 被拒（或至少被标 warn）；断言 `base_url="https://api.deepseek.com"` 仍通过（**等价改写必绿**）；断言白名单开关生效。

### W8 日志脱敏模式不统一

**具体表现**：`logging_setup._SCRUB_PATTERNS` 只认 `sk-` 与 `api_key/authorization`；`core/errors.py:56` 的 `redact()` 更全面（`sk-`/`mr-`/JWT/已登记密钥）。两套模式各写一份。
**影响**：非 `sk-` 形态的密钥若被第三方库以自由文本写进日志，可能漏网。**风险低**（已有多层脱敏）。
**改进方案**：把 `errors.redact` 作为**单源**，`logging_setup` 直接复用它（消除双份模式漂移）。
**验证方式**：断言 `mr-xxxx` 与一段 JWT 都被替换为掩码（**正面断言**，不只测「sk- 被掩码」）。

## D. 可靠性 / 并发

### W5 ✅ OCR 重启后任务永久卡「运行中」

**具体表现**：`routers/ocr.py:61` `_restore_jobs_from_disk()` 把 `jobs.json` 里的记录**原样**恢复进内存：

```python
for jid, j in data.items():
    j["cancel"] = threading.Event()
    OCR_JOBS[jid] = j          # ← 若原状态是 "running"，原样恢复
```
**无 TTL、无「非终态→失败」的重置**。执行线程已随进程死亡，任务状态永久停在 `running`。

**影响**：前端该 OCR 任务永远「运行中」，无数据损坏但**用户困惑 + 无法重试**。
**触发条件**：OCR 运行中进程被杀/重启。**爆炸半径**：单任务假运行。

**改进方案**：恢复循环里把非终态归一：
```python
if j.get("state") in (None, "running", "pending"):
    j["state"] = "interrupted"
    j["msg"] = "服务曾重启，本任务已中断，请重新提交"
```
**验证方式**：构造 `jobs.json` 含 `{"state":"running"}` → 调 `_restore_jobs_from_disk()` → 断言内存态为 `interrupted`（**注入即红**：去掉归一 → 用例必须红）。

### W6 `create_project` 同步 handler 阻塞 worker 池

**具体表现**：`routers/projects.py:86-114` `def create_project`（非 async）内同步调 `allocate(...)`，而 `allocate` 的 `sum(text.count(kw) for kw in kws)`（`quota.py:47`，120 词 × 每切片全文 `.count`）在**大输入**下是 O(切片长度 × 120)。对比 `pipeline.py:112` 的 `trial` 已改 `async + to_thread`（RV4 修复），**create 未跟上**。
**影响**：粘贴 100k 字教材时，`create_project` 占满一个 FastAPI worker 线程（默认池 40）；高并发可耗尽池。
**触发条件**：大输入 + 并发建项目（单人使用概率低，但「大输入」本身常见）。
**改进方案**：对齐 `trial`，改 `async def` + `await asyncio.to_thread(create_project_record, ...)`；顺带给 `allocate` 的 `.count` 循环加一个候选词剪枝（先按切片长度跳过明显不匹配的长词）。
**验证方式**：断言 handler 是 `async`（AST 守卫，「源码里某函数是协程」须用 AST）；性能断言：10 万字输入下 P95 建项目耗时 < 阈值。

## E. 资源 / 环境

### W9 `mineru._page_count` 失败即跳过页数闸
**具体表现**：`core/mineru.py:250-256` `except Exception: return None` → 无法判页数时**只靠体积闸**，页数闸失效。
**影响**：超页 PDF 进入 MinerU 被拒或耗时。不崩，但**闸门静默失效**。
**改进方案**：`return None` 时把「页数未知」记入任务结果并显示，而不是当作「页数合规」。同 W2 的「三态」思路。
**验证方式**：monkeypatch 让页数解析抛错 → 断言结果为「未知」而非「合规」。

### W10 无 LLM 全局成本硬上限 / 无熔断器
**具体表现**：`core/cost.py:26` 只**预估不拦截**；`quota` 是配额非预算。`LLMClient` 有超时（`llm.py:84` `timeout=300`）+ 重试 2，但**无熔断器** ⇒ 上游全挂时每个切片都等满超时（300s×重试）。
**影响**：模型跑飞时账单无闸；上游故障时整批慢。
**改进方案**：① 加可选「本次运行成本上限」，超限中止并留痕；② 加简单熔断器（连续 N 次可重试错误 → 快速失败一段时间）。
**验证方式**：断言「累计成本超上限 → 后续调用被拒」（注入即红）；断言「连续 N 次 5xx → 第 N+1 次不发起请求」（用假 client 计数）。

> **已妥善缓解、不列为薄弱点的**（审计确认）：上传大小/压缩炸弹防护（`_common.py:80-121`，600MB/200 倍解压比 + 魔数）、PDF 页数上限、数据库迁移（`db.py:448` 迁移前强制备份 + 在线备份 API + `integrity_check` + 单事务回滚 + 未知版本拒绝降级）、`import_from_json` 幂等（`INSERT OR REPLACE` + commit 后改名）、LLM JSON 提取与截断重试（`llm.py:26,137-153`）、CSP `connect-src 'self'`、Host/Origin 回环守卫（`main.py:181-202`）、密钥掩码与空串保留（`config.py:92,265,276`）。

## F. 可观测性

### W7 无跨重启的持久错误清单
**具体表现**：`core/errors.py:31` `RECENT` 是**内存缓冲**（最近 50 条），进程重启即清空。生成失败只落项目 `run.log` + 内存计数。
**影响**：用户重启后**无法回查「上次为何失败」**（除非手工翻项目目录）。**触发条件**：任何「出问题→重启」的排障路径（很常见）。
**改进方案**：把 `errors.record` 同时 append 到 `~/.medkit/logs/errors.jsonl`（滚动保留 N 天），`/api/diagnostics/errors` 合并内存 + 磁盘。
**验证方式**：断言「重新加载 diagnostics 后仍能查到重启前的错误」（模拟重启 = 清空内存 + 重新读盘）。

## 落地顺序建议

| 批次 | 内容 | 理由 |
|---|---|---|
| **1（今天可做）** | W1 原子写替换 · W3 一致性 · W8 脱敏单源 | 纯替换函数 / 单源收敛，零行为风险，收益递减最快 |
| **2** | W2 门禁三态（可区分） | 正确性风险最高，且直接呼应项目总原则 |
| **3** | W5 OCR 归一 · W7 持久错误清单 | 排障体验，改动小 |
| **4** | W6 async · W11 软删除 · W9 未知态 | 需测试配合，中等 |
| **5** | W4 SSRF（带白名单逃生口）· W10 成本闸/熔断 | 需权衡合法用法，最后做 |

**统一贯穿原则**（与项目既有纪律一致）：
1. **「通过」与「没跑」必须能区分** —— W2/W9 都是这个病的不同部位；
2. **原子写是默认，不是特例** —— W1/W3 是「同类文件一半原子一半不原子」；
3. **每个修复都配「注入即红」的反向验证** —— 否则只是加了个恒绿断言；
4. **收紧安全必须留逃生口** —— W4 若一刀切拒绝私网，会打断 Ollama 本机模型这类真实用法。

### W12（收尾时由 W6 回归暴出）——测试假绿 + 启动路径阻塞

W6 把 `create_project` 改 async 后，`test_smoke::test_project_ratio_validation` **单跑绿、全量红**。
追下去发现这是**两个独立缺陷**叠在一起，且**第一个是长期潜伏的假绿**：

**① 用例形态本身 0 次执行（假绿，HEAD 里就存在）**

```python
try:
    m.create_project(body)        # async 函数：只拿到协程，从未运行
    raise AssertionError(...)     # 不执行
except m.HTTPException as e:      # 不触发 ⇒ 断言 0 次
```
`except HTTPException` 这种写法**区分不了**「闸门拦住了」和「协程压根没跑」。它对
「配比 120% 被拒」**零信息量**，却一直计 PASS。

**② 我的第一次修法引入新错**：改 `asyncio.run(...)` ⇒ 全量跑抛
`RuntimeError: asyncio.run() cannot be called from a running event loop`
（browser 层 Playwright 同步 API 占住主线程 running-loop —— **R6-01 早有记录**，
`conftest.run_coro` fixture 就是为此而建；我没先查就自己造了轮子）。

**③ 同一条日志挖出的启动路径阻塞**：`~/.medkit/logs/errors.jsonl` 出现
`{"code":"main._open","e":"<urlopen error timed out>"}`。`main._lifespan` 的自动开浏览器线程
用 `urllib.request.urlopen` 探活 ⇒ 读 `getproxies()`（Windows 走注册表
`HKCU\...\Internet Settings`），`ProxyOverride` 命中规则时实测阻塞 >1s。
`tests/test_smoke.py` 是**独立进程**脚本（`python tests/test_smoke.py`），
**不经 conftest 的 `MEDKIT_LOG_DIR` 重定向** ⇒ 阻塞会把 R5-01 防污染哨兵拖红。

**修法（三处，缺一不可）**

| 落点 | 改动 | 判据 |
|---|---|---|
| `tests/test_smoke.py` | 改走 `run_coro`（pytest 注入）+ `_fallback_run_coro`（直跑兜底，同语义：新线程 `asyncio.run`） | 两入口都不碰主线程事件循环 |
| `tests/test_smoke.py` | 断言加**闸门探针**：`routers.projects._GATE_PROBE[0] == "ratio"` | 「抛了 400」→「**是配比这一闸**拦的」；0 次执行 ⇒ 探针 None ⇒ 红 |
| `medkit/main.py` 的 `_open` | `urllib.request.urlopen` → **裸 `socket.create_connection`** | 零代理/零注册表/零 DNS ⇒ 不再写真实家目录 |

**注入反向验证（全部按预期变红）**：① 拆掉 `_gate_probe("ratio")` 调用点 → 红；
② 回退成「不 await」旧形态 → 红；③ 探针挪到更早的教材闸 → 红。

> 教训（值得单列）：**`except SomeStatusError` 不能证明「是我这一闸拦的」**。
> 要区分「拦住了」与「没执行」，判据必须钉在一个**只有真跑进函数体才会置位**的观测点上。
