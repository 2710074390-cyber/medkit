# MedKit 后端审查报告（2026-10-22）

> **审查对象**：`medkit/` 后端（73 个源文件 / 18,867 行；FastAPI + SQLite + 本地文件存储）
> **审查方式**：静态检查基线 → AST 结构扫描 → 事务/线程/资源语义核查 → 端点级实测复现
> **结论**：**发现并修复 1 个 P0 功能缺陷**（Windows 上图片 OCR 必然 500）；另有 3 项 P1 与 2 项 P2
> 已按报告落地。**未发现**数据破坏类、注入类、越权类缺陷。

---

## 0. 一句话结论

这套后端的**工程质量高于同类个人项目一个量级**：ruff 与 mypy 双双零告警，SQLite 用每线程连接 +
WAL + `BEGIN IMMEDIATE`，31 个写事务块里**没有任何网络/LLM 调用**（实测扫描），线程与临时资源都有
`finally` 回收路径，错误存储有界且脱敏。

问题不在"写得糙"，而在**成功路径的覆盖盲区**：唯一那个 P0 恰好长在"测试从没跑过的那条分支"上——
体积超限的用例让临时文件还没来得及创建就返回了，于是"成功导入一张图"这条主路径从未被执行。

## 2. 缺陷清单

### P0-1 · 图片 OCR 导入在 Windows 上必然 500，并永久泄漏临时文件

**位置**：`medkit/routers/library.py::import_image`
**现状**：

```python
tmp = tempfile.NamedTemporaryFile(delete=False, suffix=suffix)
tmp.write(data)
tmp_path = tmp.name
try:
    markdown = await asyncio.to_thread(client.extract, tmp_path)
except MinerUError as e:
    raise HTTPException(502, ...)
finally:
    Path(tmp_path).unlink(missing_ok=True)   # ← 此时文件句柄仍然打开
```

`tmp` 是局部变量，直到函数返回才释放；`finally` 在返回**之前**执行，于是 `unlink` 面对一个
仍被本进程打开的文件。Windows 不允许删除被占用的文件：

```
PermissionError: [WinError 32] 另一个程序正在使用此文件，进程无法访问。
```

**影响**（实测复现，见下）：
1. 异常发生在 `finally` 里，会**覆盖**函数原本的返回值 → 成功识别出的文本被丢弃，前端收到 500；
2. 临时文件永远删不掉，每用一次「拍题」就在系统临时目录留一张图（长期运行累积）；
3. `MinerUError` 分支同样被这个 `PermissionError` 顶替，用户看到的是 500 而不是"OCR 失败"。

**为什么一直没被发现**：唯一覆盖该接口的用例是 `test_import_image_size_limit`，它把上限压到 8 字节，
在**创建临时文件之前**就返回 400 —— 成功路径与异常路径都没跑到 `finally` 的 `unlink`。

**复现**（直接调用端点函数，Stub 掉 MinerU）：

```text
$ python -c "… import_image(_FakeUpload(png))"
异常: PermissionError [WinError 32] … \tmpnjlifg_g.png
```

**修复**：写盘后立即 `close()`（下游只需读路径）；`finally` 里再幂等 `close()` 一次兜住"写盘前就抛异常"
的情况；`unlink` 失败降级为**留痕**（`errors.record`）而不是把整体变成 500 —— 临时文件残留是可接受的
次生问题，不该让主功能陪葬。
**优先级**：P0　**状态**：已修 + 已加回归（`test_import_image_returns_text_and_cleans_up`）

### P1-1 · 422 校验错误的 `detail` 是数组，前端会渲染成乱码

**位置**：`medkit/main.py`（缺 `RequestValidationError` 处理器）
**现状**：FastAPI 默认体是 `{"detail": [{type, loc, msg, input}, …]}`；而前端 `api()` 的错误消费是

```js
throw new Error((j.detail || j.msg || r.statusText) + code);
```

`detail` 是数组 ⇒ `new Error(array)` ⇒ 用户看到 `[{'type': 'int_parsing', 'loc': ['query', 'limit']…}]`
或 `[object Object]`，里面还带着英文内部字段路径。

**实测**：

```
GET /api/library/recommend?limit=abc  →  422
{"detail":[{"type":"int_parsing","loc":["query","limit"],"msg":"Input should be a valid integer…"}]}
```

**影响**：这是**唯一**破坏统一异常体的出口——其余错误（业务 `HTTPException`、LLM/检索/OCR/管线、
未捕获兜底）都返回 `{detail: str, error_code}`。用户侧表现为"弹了个看不懂的错"。
**修复**：新增处理器，输出 `{detail: "请求参数不合法：limit 需为整数", error_code: "VALIDATION_ERROR",
fields: [{field, msg}]}`；17 种常见 pydantic 错误类型映射为中文，未收录类型回落"格式不正确"（不再漏英文）。
新增错误码 `ErrorCode.VALIDATION_ERROR`。
**优先级**：P1　**状态**：已修 + 已加测试（含"未知类型回落"与 `_field_label` 去前缀的元守卫）

### P1-2 · 9 处上传"先整块读进内存、后判上限"

**位置**：`bank.py` / `library.py`×2 / `ocr.py` / `parse.py` / `projects.py` / `realexams.py` / `syllabus.py`×2
**现状**：清一色 `raw = await file.read()` 之后再 `if len(raw) > limit: raise 400`。
`UploadFile.read()` 会把整个上传体 materialize 进内存——**声明 200MB 上限拦不住一个 2GB 上传先吃掉
2GB**（本机同样会 OOM/疯狂换页）。其中 `bank.py`、`library.py::import_file`、`realexams.py` 三处
**此前完全没有上限**。
**修复**：`_common.read_upload_capped(file, limit, message)`：
1. 先看 multipart 解析出的 `UploadFile.size` —— 绝大多数超限场景**一块都不读**；
2. 否则按 1MB 分块累计，任一时刻越限即中止并丢弃已读缓冲；
3. 错误文案由调用方给定，**既有 9 条中文提示与状态码逐字保持不变**（前端与测试都依赖原文）。
另外 3 处原先无上限的端点补到 200MB（与 OCR/图片素材同口径）。
**优先级**：P1　**状态**：已修 + 静态守卫（禁止再出现裸 `await x.read()`，扫描面自证覆盖 9 处调用点）

### P1-3 · `/api/data/summary` 为 3 个数字整表加载，并把目录遍历了 6 遍

**位置**：`medkit/routers/data.py::data_summary`
**现状**：

```python
mistakes = lib.list_mistakes()      # SELECT * + 逐行 json.loads
knowledge = lib.list_knowledge()    # 同上
counts["mistakes"] = len(mistakes)  # 只为要一个长度
by_subject = {…for m in mistakes…}  # 再全量遍历一次
```

体积统计则是 `config / presets / library / projects / prompts` 各 `rglob` 一次，
最后 `size["total"] = _dir_size(root)` **再把整棵树走一遍** = 6 次。

**影响**：知识库上千条、项目产物累积后，打开「设置 → 数据管理」会有可感知卡顿；成本随数据量线性上升，
而它只是个统计面板。实测当前样本（25 文件 / 5.4MB）6 次遍历 16ms —— 量级不大，但**方向是错的**：
数字越小的事用了越重的读法。
**修复**：新增 `library.count_knowledge()` / `count_mistakes_by_subject()`（SQL `COUNT(*)` / `GROUP BY`，
命中既有 `subject` 索引；JSON 轨回落同口径），`data_summary` 改用它们；目录体积改为**一次遍历按首段路径归集**。
**优先级**：P1　**状态**：已修 + 测试（monkeypatch 把 `list_mistakes/knowledge` 变成"一调就炸"，
并逐项核对单次遍历的归集结果）

### P2-1 · 前端渲染了两个后端从不返回的统计键

**位置**：`medkit/web/js/app.js::loadDataMgmt` ↔ `routers/data.py`
**现状**：前端输出 `… · 复习卡 ${r.counts.review_cards} · 会话 ${r.counts.sessions}`，后端 `counts` 只有
`projects / mistakes / knowledge` ⇒ 界面上直接显示 **"复习卡 undefined · 会话 undefined"**。
**根因**：复习卡三域已随奥卡姆精简 T2 删除，`review_cards` 仅剩 db 层的遗留表（无人读取）；
而"素材会话"是活功能，后端却漏了计数。
**修复**：后端补 `counts.sessions`（`sessions/*.json` 计数，不读正文、不建目录）；前端去掉已删除域的键。
**优先级**：P2　**状态**：已修

### P2-2 · 备份只增不删，且用户看不到总量

**位置**：`medkit/routers/data.py::_build_backup_zip`
**现状**：每次备份写一个 `medkit-backup-*.zip`，**从不清理**；接口只回最近 8 份，用户无从知道磁盘上
已经堆了多少、占了多少。这是本应用磁盘增长的主要来源（一次全量备份可能数百 MB）。
**为什么没有"自动清理"**：备份是用户在灾难前的唯一安全网，**静默删除可能正好删掉灾前那一份**。
本次只做"可见化"，不做删除。
**修复**：`data_summary` 增 `backups_count` / `backups_total`（按全部备份累计），前端在超过 8 份时显示
"最近 8 份（共 N 份 / X MB）"。
**优先级**：P2　**状态**：已改（治理动作留给用户决策）

## 3. 已达标、**不要动**的部分

审查的价值一半在"指出问题"，一半在"确认哪些是资产"。以下各项经**实测/扫描**确认成立：

### 3.1 存储与事务
- `get_conn()` 每线程一连接 + `WAL` + `synchronous=NORMAL` + `busy_timeout=30000`；
  `reset_conn()` 显式 `close()`（注释里记录了"引用环导致 Windows 句柄不释放、卡住回滚"的实测教训）。
- `tx()` 写事务一律 `BEGIN IMMEDIATE`（写锁先行，杜绝读-改-写丢失更新），异常即回滚。
- **31 个事务块内没有任何 `llm / mineru / websearch / sleep / to_thread` 调用**（AST 扫描；
  扫描面已自证：31 个块全部被识别）。这一条最关键——它意味着不会出现"库被锁 5 分钟等模型返回"。

### 3.2 并发与资源生命周期
- 管线线程在 `finally` 里清理 `RUNNING / RUN_THREADS / CANCELLING`，取消走 `threading.Event` + 断点续跑。
- OCR 任务表有 24h 惰性清理、状态变更即落盘、启动时归一"运行中"为 `interrupted`、并清理孤儿 tmp。
- `errors` 存储双向有界（内存 50 / 磁盘 500 行），落盘前脱敏。

### 3.3 外部调用
- `LLMClient` 自带 `timeout=300` + `max_retries=2` + 可重试判定（timeout/429/5xx/rate limit）。
- MinerU / PDF 解析 / LLM 契约抽取均 `asyncio.to_thread`，不阻塞事件循环。

### 3.4 安全
- Host / Origin 守卫（回环放行，含 IPv6）；CSP 等响应头统一注入。
- 路径穿越三层白名单：`_safe_pid`（项目）/ `_safe_sid`（会话，含 NUL 字节教训）/ vault `_safe_vault_rel`。
- MinerU 端点 SSRF 拦截（拦云元数据/链路本地，**放行** Ollama 与内网网关——产品明确支持）。
- API Key 落盘 DPAPI 加密；错误体统一脱敏。
- 上传有魔数校验 + 压缩炸弹闸（解压总量 / 压缩比双阈值）。
- 备份**不会自包含**：`_INCLUDE_PATHS` 不含 `exports/backups`，避免"备份里套备份"的指数膨胀。

### 3.5 可观测性
- 统一异常体 + `error_code`；`errors.record(...)` 留痕（含"静默容错"语义）。
- 日志 `RotatingFileHandler` 到 `~/.medkit/logs/`，测试期由 `MEDKIT_LOG_DIR` 重定向并有防污染哨兵。

## 4. 明确未做（含理由）

| 项 | 结论 |
|---|---|
| `_run_project_impl`（389 行）、`_stage_gate1`（217 行）拆分 | 逻辑密度高、被 1160+ 用例覆盖，拆分收益（可读性）低于回归风险。**建议单独 PR**，先补"阶段边界"的特征测试再动。 |
| `cfg.load()` 加缓存 | 热路径（`require_flag` 每请求一次）确实每次都读盘 + `deepcopy`。但现有大量用例"直接写 config.json 再 load"，缓存必须按 `(path, mtime_ns, size)` 失效，收益（约 0.3ms/次）小于引入陈旧读的风险。**建议先做 profiling 再决定**。 |
| 损坏配置的 `.corrupt-{ts}.bak` | 每次 `load()` 失败都会写一份；同一秒内互相覆盖，跨秒则新增。**这不是本次改动引入的**，但属于"读路径带写副作用"。建议改为"同内容已存在则跳过"。 |
| 113 个 sync 端点改 async | **不要改**。sync 端点走线程池是阻塞 IO 的正确用法；改成 async 反而要求逐处 `to_thread`。真正需要 async 的是长任务（管线/OCR 已是后台线程 + 轮询）。 |
| 自动清理旧备份 | **有意不做**，见 P2-2。 |

## 6. 如果只能再改三件事

1. **给"成功路径"补覆盖**：本次 P0 的根因不是逻辑写错，而是**没有任何用例走过成功分支**。
   建议对每个"外部服务 + 临时资源"的端点，至少各有一条 happy-path 用例（Stub 掉外部调用）。
2. **把 `cfg.load()` 的写副作用拆出去**：读配置不该往数据目录写文件。损坏抢救应显式触发。
3. **统计类端点统一"只数不读"**：`COUNT`/`GROUP BY` 不是优化，是**接口语义**——
   面板要的是聚合结果，不是全量实体。
