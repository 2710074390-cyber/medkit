# 手机端学习平台：调研、设计与实现

> **交付**：`mobile/`（PWA，零构建 / 零 CDN / 离线可用）+ 后端同步包端点 `GET /api/bank/export/bundle`
> **范围**：只做「刷题 → 错题归纳 → 错题复习」这条闭环，其余留在桌面端
> **日期**：2026-10-27

---

## 0. 结论

这条闭环**不需要云、不需要账号、不需要改 MedKit 的安全边界**就能完整跑通。
做法是把「生成」和「消费」拆开：

```
电脑（MedKit）                        手机（PWA）
 导入 PDF / 出题 / 审核      ──导出──▶  刷题 → 错题 → 复习
 数据在 ~/.medkit                       数据在 IndexedDB
```

同步靠一个 JSON 文件（`medkit.bundle/v1`）。手机端拿到之后**完全离线工作**，
断网、地铁里、飞行模式都能刷。这条路径同时满足了三件互相拉扯的事：
数据不出本机、不需要服务器成本、手机上有原生 App 般的体验（可加到主屏）。

## 1. 调研：同类产品在做什么

### 1.1 Hyperknow（`hyperknow.io` / `agent.hyperknow.io`）

定位：**AI 学习伙伴**，把"任何学习目标"变成 1:1 AI 课程。核心能力四块：

| 能力 | 具体形态 | 对我们的意义 |
|---|---|---|
| 材料生成 | 讲课稿、速查表、测验、闪卡、交互视频 | 我们已经有的（MedKit 出题/押题卷/手册），**不需要在手机上重做** |
| 长期记忆 | 记录学习风格与进度，形成个人模型 | 我们的等价物是 **SM-2 状态 + 作答流水**，已经存在 |
| 学习计划 | 读取课程/截止日期 → 排日程，落下了自动重排 | 我们只有"到期复习"，**没有考期倒排**——这是真缺口 |
| 交互 | 可视化小黑板 + 语音打断 + 二选一提问 | 依赖实时语音与生成，成本高，手机端暂不做 |

商业模式是订阅制（Free / Pro $12 / Max），需要登录，数据在云上。
**它卖的是"生成 + 规划"，我们已经有生成，缺的是"随身消费"。**

### 1.2 值得借鉴的三点

1. **"打开即知道该做什么"**：Hyperknow 的核心体验不是功能多，而是进门就有一件事可做。
   → 我们把「复习」做成带角标的入口，到期数直接显示在底部导航上。
2. **间隔重复是留存引擎**：不是"题库有多少题"，而是"今天该复习几道"。
   → 复习队列按到期时间排序，而不是按题库顺序。
3. **记忆状态要可解释**：用户要能看出"这题我错了几次、上次错在哪"。
   → 错题卡显示 `已错 N 次` 与 `上次答的是 X`。

### 1.3 刻意不做的

| 不做的 | 理由 |
|---|---|
| 手机端 AI 生成题目 | 长文本生成成本高、要 API Key、要联网；而手机上真正需要的是"练"，不是"造" |
| 云端账号与多端实时同步 | 会推翻 README 的隐私承诺（数据只在本机），且要引入鉴权/多租户（见 `移动端迁移可行性评估_2026-10-27.md` §3） |
| 语音讲解 / 小黑板 | 依赖实时语音链路，投入产出比在现阶段最低 |
| 复刻全部 132 个端点 | 手机只需要"消费面"：刷题、错题、复习、统计 |

## 2. 同步协议：`medkit.bundle/v1`

`GET /api/bank/export/bundle?bid=&include_mistakes=1&include_attempts=1`

```jsonc
{
  "schema": "medkit.bundle/v1",      // 手机端据此判断能否读取
  "exported_at": "2026-10-27T14:00:00+08:00",
  "app_version": "0.19.0",
  "banks": [{
    "id": "b_xxx", "name": "...", "subject": "内科学",
    "items": [{
      "id": "qi_xxx",                // **稳定 id**：错题与复习进度都按它归并
      "question": "...", "type": "A1 型 · 单选", "bloom": "理解",
      "subtopic": "慢阻肺",           // 错题归纳的聚类维度
      "options": ["吸烟", "感染"], "answer": "A",   // **带答案**（离线判分）
      "analysis": "...", "case_stem": "", "source_year": "2024",
      "starred": false, "note": "", "origin_ref": {}
    }]
  }],
  "attempts":  [{ "bank_id": "...", "item_id": "...", "correct": false, "occurred_at": "..." }],
  "mistakes":  [{ "id": "m_xxx", "question": "...", "miss_count": 2, "user_answer": "B", ... }]
}
```

### 2.1 为什么这个端点必须"带答案"

`/api/bank/banks/{bid}/drill` 是**故意不带答案**的（防止前端提前看到答案）。
本端点反过来：手机端要**离线判分**，没答案就判不了。

这是有意的例外，且被测试钉死：
`tests/test_mobile_bundle.py::test_bundle_carries_answers_while_drill_does_not`
同时断言「bundle 有答案」与「drill 没答案」——防止以后有人"顺手统一"成 drill 口径。

### 2.2 为什么 id 必须稳定

手机端的错题、复习进度、作答记录全部按 `item.id` 归并。
如果每次导出换一批 id，第一次同步就是一次**学习记录清零**。
测试：`test_bundle_ids_are_stable_across_exports`。

## 3. 合并语义（最关键的一条）

> **导入永不覆盖本地的复习进度。**

同步包是「电脑端的事实」，SM-2 状态是「你在手机上练出来的记忆曲线」。
两者合并时：

| 数据 | 策略 |
|---|---|
| 题库 / 题目 | 按 id **upsert**（题目内容以最新同步包为准） |
| 作答流水 | **只补本地没有的**（按 `item_id + occurred_at` 认定同一条） |
| 错题 | 本地已有 → 只把 `wrong_count` 取两者最大值，**SRS 字段一律不动**；本地没有 → 新建，今天到期 |
| `meta.last_import` | 记录本次同步的时间与数量 |

这条规则由 `test_reimport_does_not_reset_review_progress` 把守：
先答错一题、复习一次（reps=1），再同步一遍同一个包，断言 `reps/interval/ease` 三元组不变。

**为什么这条特别重要**：如果导入重置了复习状态，表现是"每次同步后错题全部重新出现"——
用户只会觉得这 App 有病，而不会报告为一个 bug。

## 4. 复习算法：与桌面端逐值一致

`mobile/js/sm2.js` 是 `medkit/core/vault_index.py` 的严格移植：

| 项 | 值 / 规则 |
|---|---|
| 初始 ease | 2.5（下限 1.3） |
| 第一次记住 | 1 天 |
| 第二次记住 | 6 天 |
| 之后 | `max(round(interval × ease), interval + 1)` |
| 通过线 | quality ≥ 3（「模糊」也算通过） |
| ease 更新 | 通过：`e + (0.1 - (5-q)*(0.08+(5-q)*0.02))`；失败：`e - 0.2` |
| 失败 | interval=0, reps=0, state=relearning, lapses+1 |

**一个容易踩的坑：Python 的 `round()` 是 half-to-even，JS 的 `Math.round()` 是 half-up。**
直接照搬会在 `12.5 / 7.5` 这类边界上差一天，所以移植时自备了 `pyRound()`。

黄金值测试（`node mobile/test/sm2_golden.mjs`）用序列 `[5,5,5,3,1,5,4,5,5,2,5]`
覆盖「连续记住 / 模糊 / 忘了 / 重新学习」四种迁移，逐值对照桌面端输出：

```
step  q  ease  interval  reps  lapses  state
   1  5  2.6          1     1       0  learning
   2  5  2.7          6     2       0  review
   3  5  2.8         17     3       0  review
   4  3  2.66        45     4       0  review
   5  1  2.46         0     0       1  relearning
   …
```

## 5. 手机端界面

四个页签，一屏一件事：

| 页 | 内容 |
|---|---|
| **刷题** | 统计条（总题数 / 错题 / 今日已做）+ 题库列表；进库后逐题作答，单选点选即判分、多选需确认 |
| **错题** | 三档统计（错题总数 / 待复习 / 已掌握）+ **按考点聚类**的薄弱点列表，点进去只练这一组 |
| **复习** | 到期队列：先回忆 → 显示答案 → 忘了 / 模糊 / 记得；底部导航带到期数角标 |
| **数据** | 导入同步包、查看同步历史、导出复习数据（换机用）、清空本机 |

### 刻意做的几件事

- **判分后立即给出解析**，并在同一张卡里说明"已收进错题"。
- **错题卡的 SRS 状态与错题本解耦**：错题记录自带题干/选项/答案快照，
  所以即使题库重新导出、题目被删，复习列表也不会出现空白卡。
- **从错题组再练**时沿用原错题 id（`mistake_id`），不会每练一次派生一条重复错题。
- **断点续做**：同一天内退出再进同一个题库，从上次的题号继续（手机刷题常被打断）。

### 移动端硬指标（实测，390×844 / 360×740 / 768×1024）

| 指标 | 结果 |
|---|---|
| 四页横向溢出 | **0** |
| 主按钮命中区 | 全部 ≥ 44px（iOS HIG 下限） |
| 输入控件字号 | 17px（≥16px，避免 iOS 聚焦自动缩放） |
| 底部导航 | 吃 `env(safe-area-inset-bottom)`，HTML 已声明 `viewport-fit=cover` |
| 深色模式 | `prefers-color-scheme` 全套变量 |
| 离线 | Service Worker 预缓存外壳（<100KB） |

## 6. 验证

| 层 | 用例 | 结果 |
|---|---|---|
| 后端契约 | `tests/test_mobile_bundle.py`（7） | 7 passed |
| 端到端 | `tests/browser/test_mobile_app.py`（7） | 7 passed |
| 算法一致性 | `node mobile/test/sm2_golden.mjs`（18 项断言） | 全部一致 |

端到端覆盖的四条路径：
1. 空态引导指向导入（不是空白页）；
2. **完整闭环**：导入 → 刷题答错 → 判分与解析 → 错题按考点聚类 → 复习评分 → SRS 状态落库（记住 → interval=1；忘了 → interval=0、lapses=1）；
3. **重复同步不重置复习进度**（含"题目不被重复插入"）；
4. 传错文件给出人话提示，且不写入任何数据。

### 开发中实测抓到的两个真 bug

1. **`classList.add("")` 抛异常**：判分后给"未选中且不是正确答案"的选项加空 class，
   `DOMTokenList` 直接抛错 → 整个判定区不渲染（表现：点选项没反应）。
   这个坑桌面端 `bank-drill.js` 的注释里已经写过一次，移植时又踩了一遍——
   现已改成"先 remove 再按需 add"，从形状上消除。
2. **`hidden` 被 `display:grid` 盖过**：顶栏那个"更多"按钮设了 `hidden` 却仍然显示，
   点它没有任何反应。已加全局 `[hidden]{display:none!important}` 并把该按钮删掉。

## 7. 怎么用

1. 电脑端 MedKit →「题库」→ 某个题库的 `⋯` → **导出手机同步包**。
2. 文件发到手机（微信文件传输助手即可）。
3. 手机打开应用 →「数据」→ 选择文件 → 开始刷题。
4. 想"加到主屏"：手机浏览器菜单里选「添加到主屏幕」，之后像原生 App 一样全屏打开。

托管：`mobile/` 是纯静态目录，`python -m http.server` 即可本地预览；
正式用可放内网 Nginx / GitHub Pages / Vercel。详见 `mobile/README.md`。

## 8. 明确的局限与下一步

### 现在的局限（诚实列出）

| 局限 | 影响 | 备注 |
|---|---|---|
| 同步是**手动传文件** | 每次导出→传输→导入三步 | 见下方路线图第 1 项 |
| 手机上的作答**不会回流**到桌面 | 电脑端看不到手机上练了什么 | 需要反向导入（第 2 项） |
| 无考期倒排计划 | 只有"到期复习"，没有"距考试 30 天该怎么排" | Hyperknow 的强项，可后补 |
| 无 AI 讲解 | 只能看题库自带的解析 | 可做"点一下问 Agent"，但依赖联网与费用 |
| iOS 上 PWA 的存储可能被系统回收 | 长期不用可能清空数据 | 已提供「导出我的复习数据」备份；iOS 用户建议定期导出 |

### 建议的下一步（按性价比排序）

1. **局域网直连同步**（半天–1 天）：手机在同一个 WiFi 下直接拉 `bundle`，
   省掉传输文件的步骤。需要给 MedKit 加一个只读、带一次性配对码的局域网入口
   （详见 `移动端迁移可行性评估_2026-10-27.md` 路线 A）。
2. **作答回流**（1 天）：手机导出 `medkit.mobile.backup/v1`，
   桌面端加一个"导入手机记录"的端点，把 attempts/mistakes 合并进题库域。
   这样"电脑上看得到手机练了什么"，闭环才算双向。
3. **考期倒排**（2–3 天）：输入考试日期与科目，按剩余天数与薄弱点分配每日题量。
4. **PWA 分享目标**（半天，仅 Android）：从微信"分享到 MedKit"，直接导入同步包，
   把"存到文件→找文件→选文件"压成一次点击。

## 9. 为什么不是云

这不是技术能力问题，是**承诺问题**：
README 第 29 行写着「除你自己的 AI 服务商外不上传任何数据」，
而当下这套架构（回环绑定 + Host 白名单 + 零入站鉴权 + `connect-src 'self'`）
就是这句话的实现。

手机端做成 PWA + 本地存储，是唯一在**不修改这句承诺**的前提下把闭环搬到手机上的方案。
若将来确实要做多用户云服务，`移动端迁移可行性评估_2026-10-27.md` 已给出完整成本账
（3–5 周，最大成本是数据根从 import 期常量改为请求级）。
