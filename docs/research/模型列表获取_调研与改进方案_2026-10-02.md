# 模型获取功能：现状分析、调研与改进方案

> 目标：让 MedKit 的「获取模型列表」能够**展示最新可用模型**，效果对标 Cherry Studio。
> 调研日期：2026-10-02
> 方法：仓内代码逐处取证（`file:line`）+ **真实 API 实测**（DeepSeek 官方端点，2026-10-02）
> + 官方文档精读（Cherry Studio Docs / DeepWiki 技术页）。
> 结论区分「实测」「官方文档明确写明」「本报告推断」三类。

---

## 一、结论先行

| # | 结论 | 证据等级 |
|---|---|---|
| 1 | **上游 `GET /v1/models` 已经返回富元数据**（显示名 / 上下文窗口 / 输出上限 / 输入模态 / 推理档位），MedKit **把它们全部丢弃**，只留 `m.id` | **实测**（见 §2.2） |
| 2 | **「默认选中最新」是一句假承诺**：代码取 `list[0]`，即**服务商返回顺序的第一条**，无任何排序。实测顺序是 `deepseek-flash` 在前而它**不是**最新命名 | **实测**（见 §2.3） |
| 3 | 该假承诺**同时写在 UI 提示与 README** 两处（`review-desk.js:34`、README:121），无守卫 | 代码取证 |
| 4 | **「最新」没有唯一机械判据**：实测 `deepseek-flash` 的 `created` 为 `null`，按创建时间排序**不可用**；名称版本号排序对 `-pro`/`-flash`/`-exp`/日期版会误判 | **实测**（见 §3.1） |
| 5 | MedKit 的**视觉能力判定已经开始依赖模型名**（`vision.py:72` 的 `VISION_MODEL_HINTS`），而上游已给出 `input_modalities: ["text","image"]` —— **有权威字段却靠猜名字**（实测 `deepseek-flash` 带 `image`，`deepseek-v4-pro` 不带） | **实测 + 代码取证** |
| 6 | Cherry Studio 的做法是**三层合并**：静态内置目录 + 厂商覆盖 + 运行时 `listModels` 拉取；**能力字段来自静态目录而非常态拉取** | 官方文档（DeepWiki 11.2） |
| 7 | 建议方案：**「静态精选目录 + 远端实时列表」双层，取并集展示、分组呈现、按族排序**；元数据来自 a) 上游字段（若服务商给）→ b) 内置目录 → c) 命名启发式（**复用 `vision.py`，不另起一套**） | 本报告推断（见 §5） |

**一句话**：MedKit 现在的问题不是「拉不到最新模型」，而是**拉到了却不认识、排序靠服务商心情、能力靠猜名字**；改进的核心是**建一层模型目录**，把「服务商给什么」与「我们知道什么」合并起来。

## 二、现状分析（仓内取证）

### 2.1 现有实现链路

| 层 | 位置 | 行为 |
|---|---|---|
| 客户端 | `medkit/core/llm.py:253-259` | `list_models()` → `[m.id for m in self._client.models.list().data]`，**只取 id，其余字段丢弃** |
| 路由 | `medkit/routers/config.py:205-220` | `POST /api/llm/models`，入参 `{base_url, api_key}`，出参 `{ok, models:[str], msg?}` |
| 前端 | `medkit/web/js/review-desk.js:234-256` | `btn_models` → `fillModelSelect("model_gen"/"model_qc", r.models, …)` |
| 下拉填充 | `medkit/web/js/review-desk.js:14-35` | 逐条 `new Option(m, m)`；`value = saved \|\| list[0]`；提示文案「默认选最新」 |
| 静态注册表 | `medkit/core/providers.py:16-72` | 只有 `default_model` 一个字符串，**没有模型数组**、无能力字段 |
| 视觉判定 | `medkit/core/vision.py:72-94` | `VISION_MODEL_HINTS` 正面清单 + `_VL_RE` 词边界，靠**模型名**猜视觉能力 |

前端交互本身（下拉 + 「手动输入…」出口 + 「已保存不在新列表则追加并保持选中」的 A-新5 处理）是健全的，**问题集中在「数据」而非「交互」**。

### 2.2 实测：上游返回了什么，我们丢了什么

用本机配置的 DeepSeek Key 直连官方端点（2026-10-02，`openai==2.41.0`）：

```
GET https://api.deepseek.com/v1/models  →  COUNT 2
```

```json
{
  "id": "deepseek-flash",
  "created": null,
  "object": "model",
  "owned_by": "deepseek",
  "name": "DeepSeek-V4.1-Flash",          ← 人类可读显示名
  "context_window": 1048576,               ← 1M 上下文
  "max_output_tokens": 393216,
  "input_modalities": ["text", "image"],   ← 支持图像输入（权威字段！）
  "output_modalities": ["text"],
  "effort": { "supported_levels": ["low","high","max"], "default_level": "high" },
  "api_capabilities": { "anthropic_messages": { "system_prompt_update": "in-history" } }
}
```
```json
{
  "id": "deepseek-v4-pro",
  "name": "DeepSeek-V4-Pro",
  "context_window": 1048576,
  "input_modalities": ["text"],            ← 不支持图像
  "output_modalities": ["text"],
  "effort": { "supported_levels": ["low","high","max"], "default_level": "high" }
}
```

SDK 侧行为已确认（这决定了实现方式可行性）：

- `model_fields_set == {'id','object','owned_by'}` —— `Model` 只声明了这三个字段；
- **其余字段落在 `model_extra` 里**（Pydantic 保留未知字段，未丢失）；
- `model_dump()` 可完整导出全部 11 个键。

⇒ **元数据一直都在 HTTP 响应里，MedKit 在 `llm.py:255` 的列表推导里把它扔了。**
不新增任何依赖、不改协议即可拿到，**改一行就能用**。

### 2.3 实测：「默认选最新」是假的

现有 `fillModelSelect` 的核心两行是：

```js
list.forEach(m => sel.append(new Option(m, m)));   // 顺序 = 服务商返回顺序
value = saved || list[0];                          // 「最新」= 返回的第一条
```

实测返回顺序是 `["deepseek-flash", "deepseek-v4-pro"]`：

- 第 0 条是 `deepseek-flash`（显示名 `DeepSeek-V4.1-Flash`）；
- `deepseek-v4-pro` 排在后面。

**两者谁是「最新」并没有机械答案**（flash 是速度档、pro 是旗舰档，官方并未在接口里声明代际序），
但可以确定的是：**代码没有任何排序动作**，「默认选最新」这句话描述的是一个**从未发生的动作**。
`review-desk.js:34` 把它渲染成用户可见提示：

```js
$(hintId).textContent = list.length ? `已加载 ${list.length} 个模型，默认选最新` : "";
```

README 第 121 行同样写着「获取模型列表后默认选最新」。**两处声明，零处实现，零处守卫。**

> 这是本仓反复踩过的同一类缺陷：**「检查通过」与「检查没跑」没有区分开**，
> 此处是它的产品侧变体——**「文案承诺」与「代码动作」没有绑在一起**。

### 2.4 深度问题：视觉能力「有权威字段却猜名字」

`medkit/core/vision.py:72-94` 用模型名子串判定视觉能力：

```python
VISION_MODEL_HINTS = ("vision", "claude", "gemini", "gpt-4o", "gpt-4.1", "gpt-4-turbo", "gpt-5",
                      "glm-4v", "glm-4.5v", "glm-5v", "step-1v", "internvl", "minicpm-v")
_VL_RE = re.compile(r"(?:^|[-_.])vl(?:$|[-_.])")
```

`vision.py:24` 的注释明确承认这是**正面判据的保守做法**（「认不出只是退回 OCR，不会造成功能不可用」）——
在**当时**没有权威字段可用的前提下，这个设计是**正确**的。

但现在实测证明：**DeepSeek 官方接口在 `input_modalities` 里直接声明了图像能力**。
实测样本恰好构成一组反例：

| 模型 id | `input_modalities` | `looks_like_vision()` 结果 | 是否一致 |
|---|---|---|---|
| `deepseek-flash` | `["text","image"]` | **False**（名字里没有 `vision`/`vl`） | ❌ **漏判** |
| `deepseek-v4-pro` | `["text"]` | **False** | ✅ |

⇒ `deepseek-flash` 明明是支持图像的，MedKit 会因为「名字没带视觉标记」而**改走 OCR**——
多花一次 MinerU 调用、多等一轮联网，而正确答案就在响应里。

**这是「模型目录」缺失的真实代价**，不只是显示不好看。

## 三、调研：Cherry Studio 怎么做

来源：Cherry Studio 官方文档 <https://docs.cherryai.com.cn/pre-basic/providers/providers>
+ DeepWiki 技术页 <https://deepwiki.com/CherryHQ/cherry-studio/11.2-adding-a-new-provider-or-model>
（2026-10-02 精读）。

### 3.1 三层合并的数据模型

| 层 | 名称 | 载体 | 性质 |
|---|---|---|---|
| ① | Registry Presets | `packages/provider-registry/data/models.json` | 静态内置：`capabilities` / `contextWindow` / `maxOutputTokens` / `pricing` / `reasoning` |
| ② | Provider Overrides | `provider-models.json` 或 creators | 静态：厂商定制 API model ID / 价格 / endpoint 绑定 |
| ③ | User Overlay | SQLite 用户偏好 + API Key | 动态 |

运行时由 `listModels`（`src/main/ai/provider/listModels.ts`）**从服务商 live API 拉取**，
经 Strategy Registry 模式**合并进运行时注册表**，再由 `RegistryLoader.resolveModels` /
`ProviderRegistryService` / `ModelService` 组装成最终列表。

**关键洞察**：Cherry Studio 的**能力字段（vision / reasoning / 上下文 / 定价）来自静态目录层**，
而**不是**依赖每次拉取。理由是**协议的必然**——OpenAI 兼容的 `/v1/models` 在很长一段时间里
**只保证 `id`**（MedKit 实测：`model_fields_set == {'id','object','owned_by'}`，
`context_window` 等都在 `model_extra` 扩展区，属**服务商私有扩展、非协议保证**）。
Cherry Studio 面对 60+ 家服务商，绝大多数**不给**这些字段，所以必须自带目录。

### 3.2 交互流程（官方文档原文要点）

| 步骤 | 行为 | 官方原文 |
|---|---|---|
| ① | 点「**获取模型列表**」，拉取该服务商支持的模型 | 「点服务商配置页的『获取模型列表』按钮，会拉取该服务商支持的模型」 |
| ② | 弹出「**模型管理**」列表，**点模型右侧 `+` 才加入**自己的模型列表 | 「在弹出的『模型管理』列表里点模型右侧的 + 把它加入你的模型列表」 |
| ③ | **只有加入列表的模型**才出现在各处的模型选择器 | 「**只有加入列表的模型** 才会出现在各处的模型选择器里」 |
| ④ | 模型名**下方显示实际 API model ID**，防止同名不同版本混淆 | 「模型名称下方会显示服务商返回的 **实际 API 模型 ID**……先核对这行 ID」 |
| ⑤ | 「检测」按钮选一个模型测连通性 | 「点『检测』按钮、选一个模型即可测试是否配置成功」 |
| ⑥ | 服务商总开关未打开 ⇒ 其模型**不出现在选择列表** | 「务必打开服务商右上角的 **启用开关**」 |

**三个可直接借鉴的交互设计**：

1. **「发现」与「采用」分离**——拉取到的**全量**列表 ≠ 用户可用的**选用**列表。
   这解决了「一次拉回 60 个模型，下拉框里全是噪音」的问题。
2. **显示名与 API ID 双行呈现**——Cherry 明确要求核对 ID，因为「日期版、供应商前缀版等
   名称相近的模型不会再被合并」。**这正是 MedKit「最新」难题的根因**：同名不同版。
3. **能力标签驱动呈现**——`capabilities`（`function-call` / `reasoning` / `image-recognition`）
   直接用于 UI 标注，而不是让用户去猜。

### 3.3 更新机制

| 维度 | Cherry Studio | 说明 |
|---|---|---|
| 静态目录更新 | **构建期代码生成** `pnpm generate`（`scripts/generate-catalog.ts` ← `src/creators/*.ts`） | 随版本发布 |
| 运行时更新 | **用户点「获取模型列表」时拉取** | 无定时任务 |
| 定时/自动刷新 | **未发现**（文档未提及 cron / 定时同步） | — |

⇒ **连 Cherry Studio 都不做自动定时拉取。** 这是一个重要的**范围约束**：
MedKit 没有理由引入后台定时线程（何况本仓已有「后台线程隔离」的惨痛教训，
见 `AGENT_HANDOFF §7.6`）。

## 四、MedKit 与 Cherry Studio 的差距

| 维度 | Cherry Studio | MedKit 现状 | 差距性质 |
|---|---|---|---|
| 静态模型目录 | `models.json` 全量能力/定价/上下文 | `providers.py` 只有 `default_model` 字符串 | **结构性缺失** |
| 展示内容 | 显示名 + API ID 双行 + 能力标签 | **裸 ID 一行** | 信息量为零 |
| 分组 | 「模型管理」弹出层，按服务商 | 平铺一个 `<select>` | 无分组概念 |
| 发现 / 采用分离 | ✅ `+` 手动加入 | ❌ 拉回即全量塞进下拉 | 无 |
| 默认选中 | 明确标注「实际 API ID」，不强称「最新」 | 取 `list[0]` 却宣称「最新」 | **假承诺** |
| 能力字段来源 | 静态目录（权威） | 名字子串启发式（`vision.py`） | 有权威字段可取而未取 |
| 上游元数据利用 | 合并进注册表 | **全部丢弃**（`llm.py:255`） | 实测可零成本修复 |

## 五、改进方案

### 5.1 总体架构：双层目录 + 三种来源降级

```
         ┌─────────────── 展示层（前端） ───────────────┐
         │  分组：★精选（内置目录） / ⚡实时（本次拉取）   │
         │  每行：显示名 · API ID · 上下文 · 能力徽章     │
         └──────────────────┬───────────────────────────┘
                            │ 合并后的 [{id, name, ctx, caps, source}]
         ┌──────────────────┴───────────────────────────┐
         │  新增模块 core/modelcatalog（纯函数 + 零 LLM） │
         │  合并 priority:                               │
         │   ① 上游字段（若服务商给）——最权威            │
         │   ② 内置目录 MODEL_CATALOG——我们维护          │
         │   ③ 命名启发式——复用 vision.looks_like_vision │
         └──────────────────┬───────────────────────────┘
                            │
      ┌─────────────────────┴──────────────────────┐
      │ llm.list_models_detailed()                  │
      │  └─ 读 Model.model_dump()（含 model_extra）  │
      └─────────────────────────────────────────────┘
```

**三条降级路径缺一不可**：只有 ① 则自定义端点/老服务商全裸；
只有 ② 则新模型要等发版；只有 ③ 则退化成今天的样子（猜名字）。

### 5.2 最新模型的获取方式（明确回答）

**「最新」的定义必须与获取方式绑定，否则又是空承诺。** 本方案给出**可机械执行**的判据：

| 优先级 | 判据 | 适用条件 | 实测可行性 |
|---|---|---|---|
| P1 | **上游 `created` 时间戳降序** | 字段非空 | ⚠️ DeepSeek 实测为 `null`，**常不可用** |
| P2 | **内置目录里的登记顺序**（新增模型登记在数组**最前**） | 该模型在目录中 | ✅ **主力判据** |
| P3 | **名称版本号降序**（同一族内） | 名字含可比版本 | ✅ 兜底 |
| P4 | **上游返回顺序**（不排序） | 以上均不适用 | ✅ 最后兜底 |

**关键设计：把「序」变成目录里的一个显式字段，而不是算出来的。**

内置目录按「事实来源」维护，每族**显式声明推荐档**：

```python
MODEL_CATALOG = {
  "deepseek": [
    # (id, 显示名, 上下文, 能力, 推荐档)  —— 数组顺序 = 新鲜度序（新在前）
    {"id": "deepseek-v4-pro",   "name": "DeepSeek V4 Pro",
     "ctx": 1_048_576, "caps": {"reasoning": True, "vision": False}, "tier": "旗舰"},
    {"id": "deepseek-flash",    "name": "DeepSeek V4.1 Flash",
     "ctx": 1_048_576, "caps": {"reasoning": True, "vision": True},  "tier": "速度"},
  ],
}
```

> **为什么不让代码「算」最新？** 因为实测证明算不出来（`created=null`；
> `deepseek-flash` 与 `deepseek-v4-pro` 谁新无机械答案——一个是速度档、一个是旗舰档）。
> **承认「档位」而非「新旧」才是准确的语义**。UI 文案相应改为
> 「已加载 N 个模型，默认选中**推荐档**」——**说真话**。

### 5.3 更新机制（三层，全手动触发，无后台定时）

| 层 | 触发方式 | 频率 | 成本 | 落地 |
|---|---|---|---|---|
| **静态目录** | 随版本发布（人工维护 core/modelcatalog） | 每版 | 0 | 与 `providers.py` 同批，纳入 `test_providers` 同族守卫 |
| **远端拉取** | 用户点「获取模型列表」 | 用户决定 | 1 次 HTTP | 沿用现有 `POST /api/llm/models`，**不新增端点** |
| **会话缓存** | 拉取结果落 `~/.medkit/model_cache.json` | 带 TTL（建议 24h） | 0 | 前端开页即用缓存渲染，避免每次进设置都外呼 |

**明确不做**（范围约束，附理由）：

- ❌ **后台定时拉取**：Cherry Studio 都不做；本仓 `AGENT_HANDOFF §7.6` 记录了后台写盘
  污染真实 `~/.medkit` 的事故，**新增后台线程的风险远大于收益**。
- ❌ **引入 models.dev 之类外部目录**：那是另一个网络依赖 + 许可问题；且
  DeepWiki 明确记载 Cherry Studio 用的是**自建 registry**，不是外部目录。**照抄真的那个**。
- ❌ **自动把模型写进配置**：拉取只**展示**，选中才应用。
  （对齐 `A-新4`/`A-新5` 的既有原则：**不得静默覆盖用户手填的模型名**。）

### 5.4 展示范围（明确回答）

| 范围 | 内容 | 说明 |
|---|---|---|
| **必显示** | ① 显示名（`name`，缺则 `id`）② **API model ID**（小字，Cherry 明确要求核对）③ 上下文窗口 ④ 能力徽章（🖼 视觉 / 🧠 推理 / 🔧 工具） | 徽章仅在**已知**时显示，未知不显示——**不编** |
| **分组** | ★ 推荐（目录登记）/ ⚡ 最新拉取（仅在远端）/ ⏱ 最近使用（本地历史） | 三组，空组不渲染 |
| **范围** | 沿用现有语义：`model_gen`（生成）+ `model_qc`（质检）两个下拉**同源不同选中** | 不新增第三个下拉，**避免过度设计** |
| **不显示** | 定价（服务商接口不给，靠猜会误导）· 能力评分 · 「最强」之类主观标签 | 宁缺勿假 |

**「只展示加入了的」要不要抄？** 结论：**部分抄**。
MedKit 的模型数量级（每家 2~10 个）远小于 Cherry 的 60+ 家，全量平铺**不会**造成噪音；
但「**推荐 / 未推荐**」的分组**要抄**，因为它的价值不是「减噪」而是
「**让用户知道自己正在选的是不是一个新的、我们不认识的模型**」——
这正是 MedKit 应对「服务商上了新模型」的**核心提示**。

### 5.5 与视觉能力的联动（顺手闭合 §2.4 的漏判）

`vision.capability()` 的 `looks_like_vision(model)` 增加**一条更权威的前置判据**：

```
if 该模型在目录中有 caps.vision  → 用它（权威）
elif 该模型在本次拉取的元数据里有 input_modalities  → 含 "image" 即 True（权威）
else                              → 回退现有名字启发式（保守，不变）
```

**三条口径不各判一套**（对齐 `vision.py:118` 既有约定「前后端不各判一套」）。
实测收益：`deepseek-flash` 从「误判不支持图像 → 白跑一次 OCR」变为「识别为支持 → 直接读图」。

> 注意：`input_modalities` 是**服务商私有扩展**，不是协议保证 ⇒
> **它是「加分项」，不是「必需项」**，缺失时行为与今天**完全一致**（零回归）。

## 八、未决 / 待用户决策

1. **目录维护责任人**：静态目录需要随服务商发新模型更新。是**每版手工维护**，
   还是接受「新模型只在『最新拉取』组可见、目录更新滞后」？
   （本方案默认后者**可用且安全**——不收录 ≠ 不可用，只是不带徽章。）
2. **是否要「最近使用」组**：需要一个本地历史（`model_cache.json` 里顺带存）。
   收益是复用方便，成本是多一处本地状态。**默认建议：先不做**，等真实使用反馈。
3. **`model_qc` 是否也吃完整目录**：质检档通常用性价比模型，展示范围应与生成档一致；
   但「推荐档」的默认值**应不同**（生成档偏旗舰、质检档偏速度）。
