## 一、总体评价

代码成熟度显著高于同规模个人项目的常见水平，多处设计经得起推敲：

1. **契约层与门禁体系扎实**：Pydantic `extra="forbid"` 契约 + `validate_or_repair`（校验→修复重发一次→人工复核清单）+ 五道程序化门禁（选项 R 规则 / Bloom 分布 / 溯源回查 / n-gram 去重 / 临床数值锚定），且门禁结论只做 fail/warn 分级、绝不自动改写医学内容——红线意识贯穿全仓。
2. **数据安全工程过硬**：迁移前强制备份（备份失败即中止）、SQLite online backup API 一致性快照 + `integrity_check` 校验、`import_from_json` 的「commit 成功后才改文件名」（S2-28）、`row_to_dict` 损坏行返回 None 而非空壳（RV7）——都是真实事故倒逼出来的正确做法。
3. **安全面系统性好**：Host/Origin 双校验中间件（防 DNS rebinding/CSRF）、产物页独立严格 CSP（`default-src 'none'` 且正确保留 `connect-src 'self'`）、DPAPI 密钥加密、SSRF 端点守卫、统一 `errors.redact()` 脱敏、vault 路径穿越双重判据防护。
4. **工程纪律好**：事务全部 `BEGIN IMMEDIATE` 串行化、TOCTOU 安全的删除路径、快照回滚、幂等迁移（v6/v8 重升级防御）、`reset_conn` 确定性关闭句柄（WinError 32 实证修复）。

以下问题清单不改变上述结论——多数问题集中在**跨层口径一致性**与**特定边界条件**。

## 二、高严重度问题（2 项）

### H-1 `routers/config.py::put_config` 静默丢弃 `vault_dir` 与 `run_token_limit`

`put_config` 用请求体重建 `new_cfg` 时未保留 `DEFAULTS` 中的 `vault_dir`、`run_token_limit` 两个键（其余键逐字段拷贝）。后果：用户在设置页保存一次服务商配置后，错题 vault 目录被重置回默认值（界面上错题"消失"），token 预算上限被重置。

- **修复**：重建 `new_cfg` 时以 `DEFAULTS` + 现有配置为底，仅覆盖请求体显式提供的键；或对这两个键做显式透传。建议补回归测试：PUT 配置后 `vault_dir` 不变。

### H-2 判分口径跨层分叉：导出试卷 JS 不做答案大写归一

- `render/qbank_html.py` 内联试卷 JS `answersEqual(a, b)` 做集合比较但**不 `.toUpperCase()`**；
- Python 侧 `bank.answers_equal` 两侧都 `.upper()`；
- `medgen._parse_questions` 不规范化答案大小写，各门禁只校验不改写。

后果：LLM 产出小写答案（如 `"b"`）能通过全部门禁入卷；应用内判为正确，而导出的押题卷 HTML 里该题**永远判错**，且判错结果经 `syncWrong` 回流错题库 → 错题库被污染。
同样地，`normalize_item`（bank_iq）把答案统一 upper，但生成链产物没有同等归一。

- **修复**：单一归一化职责——在 `schema.QuestionItem` 的 validator 里对 `answer` 做 `.upper()`（契约层收口），试卷 JS 的 `answersEqual` 同步补 `.toUpperCase()` 作为防御。补一条跨层一致性测试：同一答案在 Python 判分与试卷 JS 判分下结论一致。

## 三、中严重度问题（5 项）

### M-1 `core/bank.py::reparse_bank` 删除与重建非原子

重解析把 `DELETE`（一个事务）与 `add_items`（第二个事务）分开：若解析/插入中途失败，题库已被清空且未回填——用户题库整库丢失（虽有 bank_sources 原文可再触发，但界面呈现为空库）。

- **修复**：DELETE + 重建放入**同一 `tx(write=True)`**；或先解析成功再开事务删除+写入。

### M-2 `core/vault.py::mistake_path` 文件名含题干 slug，改题干产生孤儿文件

vault 以「文件为真相」，但文件名由题干 slug 派生：编辑错题题干后 `mistake_path` 改变 → 新文件写入、旧文件残留（同 id 两个文件）。`vault_index` 按内容哈希寻址可部分掩盖，但目录里留下语义重复的孤儿 md，且「文件为真相」模型被弱化。

- **修复**：文件名改为稳定键（id 或 id+slug 但重命名时联动 `rename`）；编辑路径里检测旧路径并原子改名。

### M-3 `core/library.py::import_site_items` 批内重复未去重 + N+1 事务

`by_key` 在循环前一次性构建，同批导入内的重复键互相不可见（只在「与库内已有项」层面去重）；且逐条独立事务（N 条 = N 次 commit）。

- **修复**：循环内命中后立即更新 `by_key`；批量导入收敛为单事务（`replace_all`/`upsert_rows` 已具备能力）。

### M-4 `core/library.py` 删除错题不联动 vault 文件

`delete_mistake` / `batch_delete` 只删 SQL 行，不删 vault 目录下对应 md（vault 是「文件为真相」域）。结果：学习库已删的错题仍出现在 vault 检索/错题助手回答里，数据域间不一致。

- **修复**：删除时按 mistake id 联动删除/归档对应 vault 文件（vault_index 可反查 rel path），或至少在接口回执中明示 vault 副本保留。

### M-5 `core/orchestrator.py` 管线起点 `random.seed(seed)` 污染进程全局随机态

`random.seed()` 作用于进程全局 PRNG。两个项目并发/交错运行时抽样互相干扰；且同进程内任何其他用到 `random` 的代码（含第三方库）行为被悄悄改变。

- **修复**：改用局部 `rng = random.Random(seed)` 并全线透传。

## 六、整体改进建议（按优先级）

1. **建「跨层口径一致性」回归测试集**（针对 H-1/H-2 这类问题）：配置往返测试（PUT 后全部 DEFAULTS 键不丢）、判分口径测试（同一答案在 Python/试卷 JS/bank 三处结论一致）、vault 编辑往返测试。这类缺陷的共同特征是单层看都正确、跨层才分叉，只能靠端到端断言防回归。
2. **数据写操作一律单事务化**：重解析（M-1）、批量导入（M-3）收进单个 `tx`；在 `db.tx` 上加嵌套防御（L-8）后这条更容易守住。
3. **vault 文件名与 id 解耦**（M-2）：文件名用稳定 id，题干 slug 只进 front-matter；顺带打通错题删除 → vault 文件联动（M-4），消除双域漂移。
4. **随机性作用域收口**（M-5）：全局 `random.seed` 改局部 `Random` 实例，管线可复现性不受并发影响。
5. **取消路径计量对齐**（L-5）：`chat` 与 `chat_stream` 取消时都按 partial usage 快照入账，否则预算守卫在大量取消场景下系统性偏低。
6. **分层规整**（A-1）：`_strip_letter` 等文本工具下沉 core，消除 core→render 反向依赖；为后续 core 独立打包/测试铺路。
7. **前端属性内 JS 消灭计划**（L-7）：`onclick="fn('${...}')"` 模式统一改 `data-*` + `addEventListener`，从结构上消除 HTML 属性/JS 双上下文转义问题（当前仅一处失效，但模式本身脆弱）。
