## 二、已验证加固点（确认属实、未作为新发现重复上报）

以下为任务书「已知加固点」的真实性核验结论，均在 HEAD 取证：

- **Host/Origin 守卫**（main.py:128-143）：Host 取 `lower().strip()`，IPv6 分支正确提取 `[..]` 内主机名（:133-134），白名单 `{127.0.0.1,localhost,::1}`；尾点 `localhost.`、非回环、`[::2]` 均 403（测试 `test_s1_backend.py` 覆盖）。DNS rebinding 被 Host 精确匹配封死（恶意域名解析到 127.0.0.1 时 Host=恶意域名 → 403）。
- **Origin 随端口回退**：`_allowed_origins()`（main.py:63-68）读 `_local_port()`，而 `run_medkit.pick_port()` 探测到实际绑定端口后 `os.environ["MEDKIT_PORT"]=str(port)`（run_medkit.py），故 4881~4889 任一实际回退端口都被正确纳入白名单；不存在「只覆盖 4880」的缺口。
- **统一异常体 + redact**：`_err_response`（main.py:147-151）先 `errs.record` 再回 `errs.redact(str(exc))`；未捕获异常兜底（:162-172）不回显 `str(exc)`，只给类名+日志路径。`errors.py:35-43` 正则遮 `sk-` 与 `authorization/api_key:`。
- **流式断线不降级非流式、去重锁绑流生命周期**：`tutor_start_stream.gen()` 的 `finally`（library.py:817-822）无论 done/error/GeneratorExit 都 `dedupe.end(key)` + `cancel_ev.set()`；`llm.chat_stream` 的 `finally`（llm.py:178-181）全路径关闭 provider 流。未见断流回退非流式的双计费路径。
- **Key 不进 URL / public_view 脱敏**：`config.public_view`（config.py:176-201）把 `api_key`/`web_search.api_key`/`mineru.api_key`/`provider_keys.*.api_key` 全部置空、只留 `*_masked`；`/api/keys`（config.py:128）只回掩码。DPAPI 加密落盘（config.py:61-102）。
- **pid/路径消毒**：`_safe_pid`（_common.py:32-38）白名单 `[\w一-龥-]+` 拒 `/\..\`；`project_file` 双保险 `Path(name).name!=name` + 后缀白名单 + 内部文件黑名单（projects.py:267-272）；`sessions._safe_sid`（sessions.py:22-25）、`prompts` 名白名单（prompts.py:74/92）。
- **损坏 meta.json 容错**：`_read_meta_checked`（_common.py:45-59）JSON 损坏→422；解析成功但非 dict→422。
- **SQLite WAL + BEGIN IMMEDIATE**：db.py:243-259 每线程一连接、`busy_timeout=30000`、写事务 `BEGIN IMMEDIATE`，并发读-改-写串行化；FTS5 MATCH 以 `?` 参数化（explain.py:226/231），表名均为内部常量。
- **原子写**：`fsutil.write_json_atomic`（fsutil.py:38-53）唯一 tmp 名 + Windows 共享冲突重试 + finally 清理。
- **OCR 任务**：mineru.py 200MB/600 页（v4）、10MB/20 页（agent）限制齐全；ocr.py `finally` 删 tmp（:145）、启动孤儿 tmp 清理（:77-89）、jobs.json 持久化（:47-58）、取消竞态 F1（:131）。
- **命令执行面**：全仓 `grep subprocess/os.system/shell=/eval(/exec(` 无任何 Python 命中（仅前端 JS 一处正则）。

1. **M2-01（S2，已验证）** — 非流式 `tutor/start` 无双费锁。触发：同一知识点（同 `_tutor_key`）并发两次 POST `/api/library/tutor/start`（非流式降级路径）。后果：双份 LLM 计费 + 双会话。主前端走流式（已持锁），故实际暴露面小；修复成本低（guard 改持锁）。**建议优先修。**
2. **M2-02（S2，已验证）** — GET 不查 Origin + 两个带副作用 GET。触发：恶意网页 `<img src>` 指向 `/api/update/check` 或 `/api/library/cards/export/apkg`。后果：静默外呼 GitHub / 覆盖 exports 缓存；**不烧 Key、不泄密**。纵深加固，非紧急。
3. **M2-03（S3，理论）** — regen 无在飞去重。触发：重掷按钮未禁用时快速双击。后果：顺序双计费。UI 缓解已在。
4. **M2-04（S3，理论）** — 上传无魔数/zip bomb/本地 PDF 页数闸。触发：恶意/畸形 DOCX、超长本地 PDF。后果：本机 DoS。上传者即本机用户，威胁面有限。
5. **M2-05（S3，理论）** — test 类错误提示旁路 redact。当前无 Key 泄漏实例，未来新后端风险。
6. **M2-06（S3，理论）** — FTS5 jieba token 引号注入。限本机自有表，有兜底，无外带。

**整体结论**：本地服务边界（Host/Origin/CSRF/DNS rebinding）与付费 API 滥用面的主防线（Origin+JSON+无 CORS+dedupe+per-subject 信号量）在 HEAD 成立且有测试覆盖，**未发现 S0/S1 可远程利用项**。剩余问题集中在「非流式降级路径的去重不对称」与「GET 副作用/上传健壮性」两个纵深方向，均为 S2~S3。
