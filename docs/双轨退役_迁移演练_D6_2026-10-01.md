## 4. ⚠️ 演练抓到一个真缺陷（已修 + 已加守卫）

### 现象

首次演练，回滚脚本报：

```
[失败] [WinError 32] 另一个程序正在使用此文件，进程无法访问。: '…\medkit.db' -> '…\medkit.db.rollback-…'
已完成的移动：[]
```

脚本**安全失败**（什么都没动，`已完成的移动：[]`），但这暴露了一个真问题。

### 根因（逐层定位）

1. 回滚脚本 docstring 写「⚠️ 执行前必须**关闭 MedKit**」——不是客套话：进程持有
   `medkit.db` 句柄时 `rename` 必失败；
2. 但演练进程**已经**调了 `db.reset_conn()` 与 `db.shutdown()`，**仍然**被占；
3. 诊断脚本（`.workbuddy-ai/tmp/diag_d6_handle.py`）逐项试：

   | 动作 | 能否 `rename` |
   |---|---|
   | 什么都不做 | ❌ `WinError 32` |
   | `db.shutdown()` 后 | ❌ `WinError 32` |
   | `db.reset_conn()` 后 | ❌ `WinError 32` |
   | **`gc.collect()` 后** | ✅ OK（且仍剩 1 个 live `sqlite3.Connection`） |

4. 结论：**`db.reset_conn()` 旧实现只做 `_local.conn = None`**，而 `sqlite3.Connection`
   处在**引用环**里（连接 ↔ 游标），**引用计数不归零** ⇒ 要等**循环 GC** 才 `__del__`。
   在此之前 **Windows 上文件句柄一直占着 `medkit.db`**。

### 为什么这是「真缺陷」而不是「测试写法问题」

ADR-006 §4 的**回滚本质就是「把 `medkit.db` 移走」**。也就是说：**任何依赖
`reset_conn()` 来释放句柄的路径（含回滚）在 Windows 上都是不确定的**——它能不能成功
取决于循环 GC 有没有恰好跑过。这是**不可复现的偶发失败**，正是运维脚本最怕的形态。

### 修法

`medkit/core/db.py::reset_conn()` 改为**确定性关闭**：

```python
conn = getattr(_local, "conn", None)
if conn is not None:
    try:
        conn.close()
    except sqlite3.Error:
        pass
_local.conn = None
```

与 `shutdown()` 的分工：`shutdown()` 额外做 WAL 被动检查点（进程正常退出用）；
`reset_conn()` 用于「换库/换路径」这类丢弃场景。

### 守卫（**行为**判据，不是「有没有调 close」）

`tests/test_db.py::test_reset_conn_releases_db_file_handle`：迁移 + 写一行 + `reset_conn()`
⇒ **给 `medkit.db` 改名**，改不动即红。取的是**真实可观测行为**（句柄释没释放），
不是源码结构断言——后者在句柄仍被占时**照样绿**。
