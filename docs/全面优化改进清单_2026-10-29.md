# MedKit 网页版（medkit-study-app）全面优化改进清单

> 2026-10-29 · v2 修订
>
> **优化对象已更正**：`medkit-web-contest`（WorkBuddy 应用「MedKit 医学题库」），线上地址
> `https://medkit-study-app.app.workbuddy.host/?sharecode=A3MSLC6PSQ#bank`。
> 对照版本：本地版 `medkit` v0.23.0、历史网页版 `medkit-web-v2` v0.7.0。
>
> **三项硬要求（用户指定）**：
> 1. 软件标识与本地版 MedKit 一致（图标、字标、名称、品牌色）。
> 2. 加入与 `medkit-web-v2` 相同的「昵称 + 密码」登录系统。
> 3. 题库管理对齐 `medkit-web-v2`（科目 → 题库三级结构、题库元数据、按库进度、模板同步）。
>
> **必须先说清的一点**：第 2 项要求会把当前「纯前端 + localStorage」形态变成
> 「前端 + 账号服务」。在浏览器里做密码校验只能算本机账户，不是 web-v2 那种真登录；
> 要跨设备、要数据隔离，就必须有服务端。本文把它作为 P0 架构决策，并给出两条路线。

## 0. 结论先行

### 0.1 一句话判断

**当前网页版已经是一条能跑通的学习闭环，但它被三件事卡住：首屏请求太多、数据只活在单个浏览器、题库只能靠改代码更新。**

- 主链路可用：11 科 2350 题、点选判分、错题回流、SM-2 复习、错题助手、考试计划、导入导出，390px 与 1440px 均无横向溢出。
- 首屏慢的主因不是题库，是**单线程静态宿主上十余个 CSS/JS 请求排队**；线上实测 DCL 6.5~13.9s。
- 数据只在 `localStorage`（约 5MB），作答上限 8000 条，清浏览器即归零，没有账号、没有跨设备。
- 题库是静态打包的索引 + 分科文件；没有题库管理层，新增/改名/排序/下架都要重新发版。
- 错题之后仍是「问答 + 自评复习」，没有诊断、微课、同类题、延迟后测；SM-2 仍是逐错题卡片。

### 0.2 三项硬要求与架构含义

| 要求 | 当前事实 | 必须做的改动 | 优先级 |
|---|---|---|---|
| 品牌与本地 MedKit 一致 | 网页版图标是「青绿方块 + 白色加号」；本地是「青绿渐变方块 + MW 字标」。网页版副标题、meta、PWA 图标也与本地不一致 | 以本地 `pack/make_icon.py` / `medkit.ico` 为唯一品牌源，生成 SVG/PNG/ICO，统一 favicon、manifest、apple-touch-icon、OG、页面标题、侧栏字标 | P0 |
| 昵称 + 密码登录（同 web-v2） | 网页版无登录；web-v2 是 PBKDF2 200k + HMAC 签名 cookie + 每用户 SQLite | 增加账号服务；复用 web-v2 的认证与分库逻辑；首次登录迁移本地数据；支持跨设备 | P0 |
| 题库管理对齐 web-v2 | 网页版只有「内置题库 + 迁移包导入」；web-v2 有科目→题库层级、题库元数据、模板同步、按库进度、按库重刷 | 建题库模型与管理界面；稳定 id；`ensure_template` 同步新库；按库进度与断点；导入/导出/下架 | P0/P1 |

### 1.4 登录路线决策（P0 前置）

| 方案 | 做法 | 跨设备 | 安全强度 | 代价 | 结论 |
|---|---|---|---|---|---|
| **A · 真账号服务（推荐）** | 复用 web-v2：FastAPI + PBKDF2 200k + HMAC cookie + 每用户 SQLite/命名空间；静态前端调 `/api/*` | ✅ | 高 | 需要可运行后端的部署（WorkBuddy 服务型应用 / Cloudflare Workers + D1 / 自托管） | **满足「同 web-v2」** |
| B · 本机账户 | Web Crypto PBKDF2 + IndexedDB 分命名空间，密码只在本机校验 | ❌ | 低（可被绕过，数据可读） | 最小 | 只能叫「本机账户」，不能宣称账号安全 |
| C · 混合 | 默认本机，登录后可选同步；离线写队列 | ✅（登录后） | 中 | 复杂度最高 | 可作为 A 的过渡形态 |

**建议**：既然要求「跟之前登录方式一样」，选 **A**。但必须同步改写隐私文案：
从「数据只在这台设备」改为「未登录时只在本机；登录后同步到你的账号，可退出并清除」。
如果不接受数据上服务器，则只能选 B，并把「昵称密码」明确定位为「本机多用户隔离」，不能宣传为账号系统。

## 2. 功能改进项（F）

### F-01 品牌标识与本地 MedKit 统一（高）

- **现状**：网页版 `icon.svg` 是「青绿方块 + 白色加号」；本地 `pack/make_icon.py` / `medkit.ico` 是「135° 青绿渐变圆角方块 + MW 字标」。网页版页面标题、副标题「本地医学题库工坊 · 网页版」、manifest、OG、反馈弹窗都与本地不一致。
- **改进内容**：以本地 `pack/make_icon.py` 为唯一品牌源，产出 `brand/medkit-icon.svg` + 16/32/48/64/128/256 ICO + 192/512 PNG + maskable 512；更新 `icon.svg`、`manifest.webmanifest`、`<link rel=icon>`、`apple-touch-icon`、OG 图、页面标题、侧栏字标、反馈弹窗、版本号展示。品牌名统一为「MedKit · 医学题库工坊」；「网页版」只作为标题后缀/环境标识，不进入图标字标。品牌色以本地 `tokens.css` 为准（暖纸底 + 墨绿主色），先统一图标与字标，再评估整套令牌同步。
- **参考依据**：A `pack/make_icon.py`、`medkit.ico`、`medkit/web/css/tokens.css`；C `icon.svg`、`manifest.webmanifest`；`[STD-2]`。
- **验收标准**：16/32/64/256 四档与本地图标并排像素级同构（圆角、渐变方向、MW 字重、留白）；PWA 安装图标为 MW；全站不再出现加号图标；标题/字标/副标题一致；截图基线入库；一条脚本可重新生成全部尺寸。

### F-02 昵称 + 密码登录（同 web-v2）（高）

- **现状**：网页版无登录；数据只在本浏览器。web-v2 的登录是「昵称不存在即注册、存在则验密」，PBKDF2-HMAC-SHA256 200,000 次、16 字节盐、HMAC-SHA256 签名 cookie 30 天、每用户独立 SQLite。
- **改进内容**：增加账号服务，复用 web-v2 的认证与分库逻辑；前端提供登录卡（昵称、密码、进入）、退出、当前昵称；首次登录把本机 `localStorage` 数据迁移到账号（合并/覆盖二选一，预演计数）；登录后账号数据跨设备可用；未登录仍可本地试用，但明确标注「本机模式」。
- **参考依据**：B `store.py`（`_ensure_auth_schema`、PBKDF2、`make_session/parse_session`、每用户 `user_db`）、B `app.py` `/api/enter` `/api/logout` `/api/me`；`[STD-4]` OWASP ASVS。
- **验收标准**：注册/登录/退出/会话过期四态可用；错误密码不泄露「昵称是否存在」以外的信息；密码不以明文/可逆形式落盘；同账号两台设备数据一致；本地数据迁移不丢作答/错题/笔记；暴力破解有限流；cookie `HttpOnly` + `SameSite`；跨用户越权 403/404。
- **前置**：1.4 方案 A 或 C；若选 B，本项降级为「本机账户」，验收删去跨设备与安全强度两项。

### F-03 题库管理对齐 web-v2（高）

- **现状**：当前只有 `data/index.json` + 每科 JSON + 迁移包导入；没有题库管理层，无法改名、排序、启用/停用、单库导入导出、按库看进度。web-v2 有 `banks` 表（id/name/coverage/subject_id/subject_name/variant/variant_order/subject_order）、`bank_items`、`bank_attempts`、`bank_progress`，并有 `ensure_template()` 把新库同步给所有用户。
- **改进内容**：建立「科目 → 题库 → 题目」三级模型；题库元数据含 `id/name/subject_id/subject_name/variant/variant_order/subject_order/term/source/license/item_count/updated_at/enabled`；新增「题库管理」界面：按科目分组、改名、排序、启用/停用、删除、单库导入/导出、查看进度与正确率、按库重刷；新内置库通过模板同步进入老用户，保留作答与错题；稳定 id（`科目名#序号` 或 `bank_id#item_id`）。

## 3. 架构与技术栈优化项（A）

### A-01 静态托管性能架构（高）

- **现状**：`index.html` 有 4 个 CSS + 8 个 JS（共 12 个静态请求），宿主为单线程静态服务，请求排队；线上实测 DCL 6.5~13.9s，HTML 本身 4.6s；没有 gzip。
- **改进内容**：部署侧把 4 CSS 合并为 1、8 JS 合并为 1（源文件仍可拆分，产物合并），或内联首屏关键 CSS；静态资源加内容哈希与长缓存；启用 gzip/brotli；优先 HTTP/2 或 CDN（Cloudflare Pages）；把「题库索引」改为 `<link rel=preload>` 但避免阻塞 CSS/JS。
- **参考依据**：C `docs/体验测试_2026-10-29.md` 第四节 P0；B `GZipMiddleware` + immutable 缓存；Web Vitals。
- **验收标准**：首屏关键请求 ≤4；gzip 开启；DCL <3s（线上中位数）；二次访问命中缓存；瀑布图无 CSS/JS 被题库阻塞；CI 有请求数/体积预算。

### A-02 账号服务与后端边界（高）

- **现状**：C 纯前端无后端；登录、跨设备、题库服务端管理都没有落点。
- **改进内容**：新增最小账号服务：`POST /api/enter`、`POST /api/logout`、`GET /api/me`；密码 PBKDF2 200k；HMAC 签名 cookie；每用户数据命名空间；题库/作答/错题/进度服务端表；静态前端只做展示与缓存。部署可选 WorkBuddy 服务型应用、Cloudflare Workers + D1、或自托管 FastAPI。**禁止在客户端做密码校验冒充登录。**
- **参考依据**：B `store.py`/`app.py`；`[STD-4]` OWASP ASVS；1.4 决策表。
- **验收标准**：认证端点契约测试；每用户隔离；cookie 安全属性；限流；CSRF；无明文密码；部署文档与回滚步骤。

### A-03 数据层：localStorage → IndexedDB + 同步队列（高）

- **现状**：所有学习数据在 `localStorage`，约 5MB；作答上限 8000 条；`_set` 静默吞掉 `QuotaExceededError`；没有 schema 版本；清浏览器即归零。
- **改进内容**：作答流水、错题、笔记、收藏、复习卡迁到 IndexedDB（大容量、异步、事务）；`localStorage` 只留主题、目标、会话等小配置；建立 `schema_version` 与迁移；写入失败显式提示并回滚；登录后加同步队列与冲突解决。
- **参考依据**：C `Store`；B 每用户 SQLite；IndexedDB 事务模型；`[STD-4]` 数据完整性。
- **验收标准**：10 万条作答可读写；配额不足有可操作提示且不丢已写数据；v1→v2 迁移逐值一致；导出/导入往返相等；离线写入联网后同步不重复。

### A-04 题库模型、种子与模板同步（高）

- **现状**：C 是 `index.json` + 分科文件 + 用户导入题库按名称合并；没有题库实体、没有元数据、没有模板同步。
- **改进内容**：定义 `subjects/banks/items/bank_progress` 模型；题库元数据见 F-03；稳定 id；种子构建；`ensure_template()` 登录时把新库同步到用户命名空间；题库版本与内容哈希；重复题三选一。
- **参考依据**：B `store.py` schema 与 `ensure_template`；B `build_seed.py`。
- **验收标准**：新库同步不丢作答；题库改名/排序/停用即时生效；稳定 id 往返；内容版本可追溯；单库导入失败回滚。

### A-05 前端模块化与加载顺序（中）

- **现状**：8 个经典脚本共享全局作用域，加载顺序即隐式契约；`app.js` 1044 行（超过 800 行约束），`bank-drill.js` 740 行；大量内联 `onclick`。
- **改进内容**：把 `app.js` 按「路由/今天/刷题/错题/题库/设置/AI/数据」拆分到 ≤800 行；引入轻量 `MedKit.registerView({init,destroy})`；显式初始化；保留零构建；把内联处理器逐步收敛为事件委托；加加载顺序契约测试。
- **参考依据**：A 前端分域耦合守卫；C README「经典脚本共享全局作用域」。
- **验收标准**：单文件 ≤800 行；删除非核心模块不影响核心；无全局命名冲突；事件委托覆盖主要按钮；eslint 0；加载顺序测试通过。

### A-06 API 契约、错误、分页与幂等（中）

- **现状**：C 无 API；B 有 `{detail}` 错误与 `client_id` 幂等，但成功体不统一、分页不统一。
- **改进内容**：账号服务统一 `{data, meta}`；错误 `{detail, error_code, request_id}`；分页 `cursor/limit/total`；写操作支持 `Idempotency-Key`；前端统一错误解析器与重试。
- **参考依据**：B API 兼容做法；`[BE]`；RFC 9457。
- **验收标准**：重复判分/导入不重复写；分页契约测试；错误有中文与字段定位；前端不再显示 `[object Object]`。

### A-07 构建、缓存与 sharecode 部署（高）

- **现状**：无构建；资源无哈希；静态宿主对每个请求校验 sharecode，manifest/icon 需前端补参数；没有部署前检查。
- **改进内容**：加一个「部署产物」步骤（源文件不变）：合并/压缩/哈希/生成 manifest；sharecode 处理集中到一个小函数；部署前检查（题库索引、manifest、icon、CSP、缓存头）；版本号与题库版本写进页面；回滚脚本。
- **参考依据**：C `index.html` sharecode 脚本；B `preflight_deploy.py`；Cloudflare Pages。
- **验收标准**：资源名带 hash；二次访问 304/immutable；manifest/icon 不再 403；部署前检查 exit 0 才发布；回滚可回到上一版本。

### A-08 可观测性与诊断包（中）

- **现状**：只有 `window.onerror` toast 与邮件反馈；没有本地错误日志、版本、请求耗时、题库版本。
- **改进内容**：本地环形错误日志（IndexedDB）；一键导出脱敏诊断包（版本、浏览器、题库版本、最近错误、最近请求耗时）；匿名上报默认关；反馈邮件自动附诊断包摘要。
- **参考依据**：A `errors.record` / 诊断入口；`[STD-4]` 最小必要。
- **验收标准**：一次失败可从一个 id 串起；诊断包 0 密钥/PII；导出 <5MB；用户可预览后再发送。

### A-09 前端安全基线（高）

- **现状**：静态页有内联脚本与大量内联 `onclick`；无 CSP；BYOK Key 存在 `localStorage`；AI 回答经 `mdRender`（已先转义，风险较低）。
- **改进内容**：加 CSP（先允许 `'unsafe-inline'` 过渡，逐步改事件委托/nonce）；审计所有 `innerHTML` 拼接；BYOK Key 迁到 IndexedDB + 可选「仅本次会话」；提供「清除 Key」；后端加 CSRF/限流；禁止把 Key 写进日志/诊断包。
- **参考依据**：`[STD-4]` OWASP ASVS；C `md.js` 先转义口径；B CSP。
- **验收标准**：CSP 无严重报错；XSS 样本注入不执行；Key 不出现在日志/导出；清除 Key 后请求不再带；后端限流。

### A-10 迁移、版本与回滚（中）

## 5. 性能与稳定性提升项（P）

### P-01 首屏请求数与单线程网关（高）

- **现状**：4 CSS + 8 JS + HTML + 题库索引；宿主单线程，请求排队；线上 DCL 6.5~13.9s，HTML 4.6s。
- **改进内容**：合并 CSS/JS 产物；关键 CSS 内联；题库索引 preload 但不阻塞；换 HTTP/2/CDN；设置静态资源缓存；避免在 head 预取大文件。
- **参考依据**：C 体验测试 P0；A-01。
- **验收标准**：关键请求 ≤4；DCL <3s；CSS/JS 不再被题库阻塞；瀑布图可复核。

### P-02 压缩、缓存与 CDN（高）

- **现状**：宿主未 gzip；资源无哈希；二次访问可能重新验证甚至重下。
- **改进内容**：gzip/brotli；`Cache-Control: immutable` + 哈希；HTML `no-cache` + ETag；CDN 边缘缓存；题库索引短缓存、分科文件长缓存。
- **参考依据**：B GZip + immutable；Cloudflare Pages；Web Vitals。
- **验收标准**：JS/CSS gzip 后体积下降 ≥60%；二次访问命中缓存；题库索引更新可即时生效；分科文件长缓存不串版本。

### P-03 题库懒加载与预取（中）

- **现状**：已做索引 + 分科懒加载；开始刷某科时才拉 90~384KB；没有预取下一页/下一科。
- **改进内容**：科目卡 hover/聚焦预取；进入答题前预取下一科；分页/分组；失败可重试；缓存版本。
- **参考依据**：C 体验测试第四节；B 预取 8 题；`[PROD-4]`。
- **验收标准**：开始答题等待 <1s（已缓存）；切科目无白屏；预取不拖慢首屏；失败有重试。

### P-04 localStorage 配额、容量与 8000 上限（高）

- **现状**：`localStorage` 约 5MB；`recordAttempt` 超过 8000 条裁掉最旧；`_set` 静默吞掉配额错误；清浏览器即归零。
- **改进内容**：迁 IndexedDB；容量/条数上限可配置；超限前提示并归档；导出备份；登录后服务端同步；写入失败显式回滚。
- **参考依据**：C `Store.recordAttempt/_set`；B SQLite；A-03。
- **验收标准**：10 万条流水可读写；配额不足有提示且不丢已写；导出/导入往返；清浏览器后可从账号恢复。

### P-05 AI 请求超时、取消、流式与重试（中）

- **现状**：`AI._byokChat` 没有超时/取消；`stream:false`；CORS 失败只给一句提示；没有成本预估。
- **改进内容**：AbortController + 超时；取消按钮；流式输出（SSE/ReadableStream）；指数退避重试；错误分类（401/429/CORS/超时）；请求前显示参考成本。
- **参考依据**：B 超时重试；A 成本透明；`[STD-3]` 错误恢复。
- **验收标准**：30s 超时可取消；429 有退避提示；CORS 错误可操作；流式不阻塞 UI；成本预估可见。

### P-06 写入原子性、幂等与冲突（中）

- **现状**：`localStorage` 单键写入不是事务；判分/导入重试可能重复；导入已有整体回滚（好）。
- **改进内容**：IndexedDB 事务；判分/导入/同步加 `client_id`；重复请求回放；冲突提示合并/覆盖；失败快照回滚。
- **参考依据**：B `idx_att_client`；C `importPackage`；A-06。
- **验收标准**：重复判分只落一次；导入失败不留半包；同步冲突不静默覆盖；单测注入重试。

### P-07 静态资源版本与完整性（中）

- **现状**：无内容哈希；题库索引与分科文件版本未绑定；更新后可能新旧混用。
- **改进内容**：资源 hash；`bank_version` 与 `app_version` 写入清单；加载时校验；不匹配提示刷新；回滚保留上一版。
- **参考依据**：A 版本单源；B 发布一致性。
- **验收标准**：新旧资源不混用；题库版本可查；更新提示；回滚可用。

### P-08 离线与 PWA 缓存（中）

- **现状**：有 manifest 无 Service Worker；离线打开不保证。
- **改进内容**：SW 预缓存壳与索引；分科文件 runtime cache；离线写队列；更新提示；缓存清理。
- **参考依据**：F-14；`[STD-2]`。
- **验收标准**：断网可打开已缓存页面；已缓存科目可刷；联网后同步；不缓存 Key。

### P-09 错误监控与诊断（中）

- **现状**：只有 console 与 toast；没有版本/题库版本/最近请求。
- **改进内容**：本地错误日志；诊断包；反馈自动附摘要；匿名上报默认关；错误码。
- **参考依据**：A-08；`[STD-4]`。
- **验收标准**：一次失败可串起；诊断包 0 密钥；导出 <5MB。

### P-10 性能回归门禁（中）

- **现状**：有 Node 测试 36 项，但没有首屏/请求数/体积预算。
- **改进内容**：CI 检查关键请求数、JS/CSS 体积、题库索引一致性、DCL 本地基线；超预算失败；截图基线。
- **参考依据**：C `tools/ux-check.mjs`、`build_questions.py --check`；A 性能门禁。
- **验收标准**：请求数/体积超预算即红；题库一致性校验；本地 DCL 基线可复现。

### 7.4 明确不做

1. **不在浏览器里做「假登录」并宣称安全**：密码校验必须在服务端；本机账户只能叫本机账户。
2. **不把 BYOK Key 上传到账号服务**：Key 只属于设备；同步数据不包含 Key。
3. **不做通用聊天助手**：护城河是内置题库 + 错题 + 可核引用 + 本地/账号数据。
4. **不自建内容库**：题库版权归上游；只做可审计的批次同步与下架。
5. **不做没有常模的分数预测**：做「准备度」，标注「非预测」。
6. **不先做复杂云多租户**：先完成最小账号服务与跨设备，再谈配额/计费。
7. **不做排行榜/惩罚式连胜/社区主路径**：备考人群的断签时刻是流失高发点。
8. **不破坏「未登录也能刷」**：登录是增强，不是门槛；本地模式必须保留。
9. **不引入构建链到源文件**：源文件保持零构建；合并/压缩只发生在部署产物。
10. **不保留旧加号图标/旧品牌文案**：品牌单源，防止回流。

## 附：给实施者的顺序

1. **先换标识**：MW 图标 + 字标 + PWA 图标 + 品牌文案；这是零风险、最快让用户认出来的改动。
2. **再定登录路线**：要跨设备就上最小账号服务；不要用浏览器密码校验冒充账号系统。
3. **然后做题库模型**：科目 → 题库 → 题目；先有稳定 id 和模板同步，再做管理界面。
4. **同时治首屏**：合并 CSS/JS、gzip、缓存、CDN；否则后面每加一个功能都会更慢。
5. **最后做学习闭环**：FSRS → 题目统计 → 延迟后测 → 诊断/支架。
